## Verdict

The edges are mostly well made at the unit level (argv-only Exec with process groups and capped output, a leased and holder-gated push in the worker, a result-id-fenced report, a careful key proxy with an allowlist, a real model bound by a trace walk), but the layer does not keep its central safety promise, and several of the worker's classification rules fail open on exactly the inputs the doc says they must not. The single worst thing: guarantee 4 ("base advances only to a sha whose checks passed at that exact sha, from the base tip it was gated on") rests on GitHub refusing a moved base ("a base whose protection requires branches up to date"), and nothing in the tree checks that the repository's protection says so (`stream add` does not; `grep` for strict/up-to-date finds nothing); the only defence is an `ls-remote` just before `gh pr merge` (`edge/git/land.go:215-223`), a check-then-act window the model (`tla/LandEdge.tla`, one atomic `Pass`) cannot see. Behind it: rate limits and transient gh/git errors become coordinator judgements instead of faults (the `Forge` rest is never read), a harness whose output contains `nova-reserve:` is re-run forever as "no slot", `Alive` reads `/proc` so a restart on a Mac cannot adopt or kill a live harness, and the claude and codex adapters are never given a config directory so they cannot log in. The layer is sound as a design and not yet sound as code; it should not lock.

## Defects

Ranked. Severity: blocker, serious, minor, nit.

1. **blocker. A moved base can be merged untested; the "protection requires up to date" the guarantee leans on is never checked.** `edge/git/land.go:215-228`: the pass re-reads base (`now != res.BaseTip`), then calls `fg.Merge`, which is `gh pr merge --<method> --match-head-commit <sha>` (`edge/forge/forge.go:443`) with no base check at all (`PRInfo.BaseRef` is never compared; the doc's Built text says Merge "verifies PR base and head SHA before fast-forwarding", `docs/LAYER-4-EDGES.md:532-533`, and the code does none of that). If base moves between the `ls-remote` and GitHub's merge (a `gh repo view` call for the merge method may even sit between them, `forge.go:438`), GitHub makes a merge commit of the new base and the PR head: a tree CI never saw on base. Doc line 148-149 says `stream add` refuses an unprotected base; `cmd/nova-sprint/admit.go:101-120` reads only required status check names, never `required_status_checks.strict` or a ruleset's up-to-date rule. Repair: read `strict` (and rulesets) at `stream add` and refuse without it, and have `Merge` compare the PR's `baseRefOid` (or use the merge API with `sha` plus an expected base) so a moved base is refused by the call itself.

2. **serious. Rate limits and transient failures become judgements; the rest is never consulted.** `edge/git/land.go:197-201` (PR/OpenPR error -> `pr_unopenable`), `:223-227` (any Merge error, including `*forge.FaultError` and an exec timeout, -> `merge_refused` "GitHub refused the merge"), `:184-187` (any Push error, including a timeout -> `branch_failed`). `landItem` and the comment at `land.go:14-16` make every outcome except landed/pending/absent/base-moved "a judgement for the coordinator". Meanwhile `Client.RestedUntil` and `FaultRateLimit` have no non-test caller (grep). Guarantee 11 and the doc ("a rate limit rests the identity and fails no card", "a fault to its caller that spends nothing") are broken in the same way for the whole forge. A merge that succeeded but whose follow-up `gh pr view` hit the 30 s timeout or an exhausted token bucket (`forge.go:446-449`) is reported as refused, and with a squash or rebase method (`forge.go:481-487`) the retry cannot recognise it as landed (heads are not ancestors of base, `land.go:85`). Repair: return `*FaultError` and `ExecError` from `LandPass` as the error (the "fault" outcome), keep outcomes for facts, and have run rest the landing until `RestedUntil`.

3. **serious. A harness whose output mentions `nova-reserve:` is treated as "no slot" and re-run forever.** `edge/worker/runner.go:1161`: exit 1 plus the substring `nova-reserve:` anywhere in the combined stdout/stderr of the wall command, unless it also contains `nova-reserve: HELD`, returns `ErrNoSlot`. The harness's own output and a `go test` run's output are in that string (this repository's own cards print `nova-reserve:` lines). `runStep_internal` (`:549-553`) then puts the job back to `staged` and the next pass runs the harness again, never reporting: unbounded model spend with no verdict. The same rule applied to `RunTest` is worse the other way: `rebaseAndTestStep_internal` (`:678-686`) reads any `err` from `RunTest`, including `ErrNoSlot`, as "tests red" and reports `fail`, which bounces the card for a busy bench (doc line 270 "no slot within the wait is no start yet, never a failure"; guarantee 11). The doc itself bans substring-scanning of agent prose and test output for classification. Repair: have nova-reserve signal "no slot" with a distinct exit code or a file/JSON, and handle `ErrNoSlot` from `RunTest` by keeping the job at `harvested` to retry.

4. **serious. `OSProcessTable.Alive` only works on Linux, so on a Mac restart cannot adopt or kill a harness.** `edge/worker/runner.go:93-104`: after `Kill(pid,0)` it trusts the in-process `liveProcNonces_internal` map (empty after a restart) and otherwise reads `/proc/<pid>/environ`; on darwin that read fails and `Alive` returns false. Consequences on a macOS bench (the Mac Studio and Mac minis are benches): a harness that survived the worker is judged gone, so `recoverWorkingJob_internal` (`recover.go:122`) re-stages and runs a second harness on the same card (the `RunnerRestartSpawnsSecondHarness` witness, with the guard defeated), and `Kill` (`runner.go:105-108`) is a no-op, so `finalJob_internal`/`withdrawRunningJob_internal` (`recover.go:103-108`) removes the job directory under a live harness (the v1 incident the doc names, LAYER-4 line 359). The trace walk uses `fakeProcTable` (`edge/worker/trace_test.go:140`), so no test touches the real predicate. Repair: carry the nonce by another channel (process start time via `ps -o lstart= -p`, or a pid file locked by the harness's parent) on every OS the fleet has, with a test on the real table.

5. **serious. The claude and codex adapters can never log in.** `ClaudeHarness.ConfigDir`/`CodexHarness.ConfigDir` are never assigned outside `harness.go` (grep `ConfigDir`: harness.go only; `cmd/nova-worker/main.go` has no flag for it and `NewHarness` returns zero values, `harness.go:61-63`). `Command` emits `CLAUDE_CONFIG_DIR`/`CODEX_HOME` only when it is set (`:149,158`), takes its env from `baseWallEnv_internal` (not the worker's environment), and `SanitizeWallEnv` sets `HOME=<job>/home` (`:441-462`), so the harness starts with an empty home, no config dir and no provider key. The doc (line 327) says a logging-in harness "keeps its credentials in its own store, granted read-only into the wall". When it is set, `Needs.Writes` makes it `--write`, not read-only, with `NetOpen` true (`harness.go:108,113,379`): an agent can read and overwrite its own login and send it anywhere. Repair: add `--claude-config-dir`/`--codex-home` flags (read-only unless the harness must write), or copy a minimal credential file into the job home; document the weaker wall as shown on the row.

6. **serious. A signalled child is `exit -1` with no error, and the worker classifies that as a card failure.** `edge/exec.go:156-159`: `exec.ExitError.ExitCode()` is -1 for a signal death and is returned as `Result{ExitCode:-1}, nil` (run above). `classifyExitAndTail_internal`/`ClassifyJob` know only 134 and 137 (`harness.go:255,280`), and `isInfraFault_internal` (`runner.go:570-579`) tests `errors.As(runErr, &exec.ExitError)` which `OSExec` never returns. A wall killed by the OOM killer or `kill -9` therefore yields "fail: no verdict" and bounces the card, which `Runner.tla` forbids (`FaultSpendsNoAttemptOrBounce`, `Die` is always a fault). Repair: have `Exec` report `Signal int` and map any signal death (not only the worker's own cancel) to a fault.

7. **serious. The ledger merge is dead in production.** `run/edges.go:131` builds `git.LandRequest` without `Ledgers`; the only producers of `LedgerRule`/`Ledgers` outside tests are the types (`edge/git/land.go:40`, `edge/request.go:30`). The doc (steps 2, line 128-131; "Ledger files ... merged entry by entry") promises it, so any shared ledger file conflicting between two heads becomes a `conflict` judgement. Repair: wire policy's ledger list into the request, or delete `LedgerRule`, `resolveLedgers_internal` and `unionLines_internal` and the doc paragraph.

8. **serious. `git.LsRemote` of a sha fetches every ref on origin one by one.** `edge/git/git.go:200-242`: when the sha is not itself a tip, it lists all refs (including `refs/pull/*`), then for each tip does `git fetch origin <tip>` followed by `merge-base --is-ancestor`, each with a 60 s `PushTimeout`, serially and with no total bound. On a repo with hundreds of card branches and PR refs a head that was already merged away costs hundreds of fetches. "On origin" is also any ref, not "the head on the branch at origin" (LAYER-4 line 105). Used by `Client.LsRemote` callers passing a sha; the landing passes refs, so the exposure is the ancestry probes admission and `finish` make. Repair: ask `git branch -r --contains` after one fetch of all heads, or fetch the branch the card names.

9. **serious. A non-conflict rebase failure bounces the card.** `edge/worker/runner.go:667-669`: any rebase error that is not a `ConflictError` or `FetchError` (git lock, timeout, disk full, `ExecError`) sets `fail` ("rebase failed: ..."). The doc (line 303-304, 313) says only a rebase conflict is a `fail`; a bench fault is a `fault` (guarantee 11). `OSGitOps.RebaseOntoStream` (`:1003-1022`) returns the raw error for anything but unmerged files. Repair: classify the `default` case as `fault`.

10. **serious. Nothing pushes with the row's token, and the worker's git runs with the host's own credentials.** The doc (lines 216-218, 275-276, and the "git token is used only by the runner") says workers push with their row's token; `OSGitOps.runGit_internal` (`runner.go:1056-1068`) passes only `PATH`, `HOME` and `GIT_TERMINAL_PROMPT`, so whatever the host's git config and keychain answer pushes (grep `Token` in `edge/worker`: none). Whether a person's login is behind that helper is not decided anywhere (see Questions). Repair: a credential helper env as in `edge/git.credentialEnv_internal`, or state in the doc that workers push as the host login.

11. **serious (test red at the base commit). `cmd/nova-worker` fixture deals a `ready` consumer; the worker never takes `ready`.** `cmd/nova-worker/break_test.go:80` fails (above). `planPass_internal` (`pass.go:215-222`) starts jobs for `next.Working` only, "the deal is the take (defect 52)"; the doc's step 2 (`LAYER-4-EDGES.md:254`) and the restart paragraph ("Ready consumers are taken as at a wake") still describe taking `ready` ones. 12. **minor. `merge` that fails for a reason other than conflict is typed `MergeConflict` with no files; cleanup stops at the first failed command; a timeout leaves the clone mid-merge.** `edge/git/git.go:323-335`: a merge exit code with no unmerged file (untracked file in the way, unrelated histories, an unreachable head) returns `MergeConflict` with `Conflicts` empty, which `land.go:171-175` turns into a rung-3 conflict judgement naming nothing. `cleanup_internal` (`:394-402`) returns at the first failure, so a failed `merge --abort` skips `reset --hard onto`. `mergeOneHead_internal` returns the exec error without any cleanup on a timeout (`:311-312`), and nothing at the top of `MergeGroup` resets the clone (`:279`: `checkout --detach` fails on an unmerged index), so one timeout can wedge the landing clone. ## Model vs code

- `tla/Runner.tla:54-58` `Wake` is a copy of the crash budget decrement (`env.crashes + 1`, nothing else changes). The doc says Wake covers "duplicated, lost" wakes; the action only burns the single crash the size allows, which prunes the state space (with `MaxCrashes = 1`, a crash after a `Wake` is impossible). `PassStart` is what actually models a wake. Replace it with a no-op stutter or delete it; the trace map `a = "Wake" -> Wake` follows.
- `Withdraw` (`Runner.tla:208-217`) requires `harnessAlive[c] = 0` and `jobState[c] \in RetireStates` (no `running`, no `reporting`). The code's main withdraw path is a running harness (`cancelRunning_internal`, `withdrawRunningJob_internal`, `runAndHarvest_internal` `pass.go:421-428`) and a record at `reporting` whose card went final (`finalJob_internal`). Neither is checked; defect 4 lives exactly there.
- `Restart` (`Runner.tla:272-275`) is `harnessAlive' = harnessAlive`: adoption always works. The code's decision is the `Alive` predicate; the trace walk replaces it with `fakeProcTable` (`trace_test.go:140`), so "never spawn a second harness" is a model assumption, not a checked behaviour (defect 4 on darwin).
- `Report`/`Clean` are two steps in the model (`Report` then `Clean` needs `jobDir.pushed`); the code's `cleanJobDir_internal` can keep the directory at `recorded` forever when the origin tip is not exactly `PushedHead` (`runner.go:738-745`), a state the model has no name for (`recorded` is not in `RetireStates`, so `Retire` cannot fire either) and `Liveness` for a final consumer's directory (`FinalDirRemoved`) is checked only for `fail`, not for a `done` card kept as "kept-unconfirmed-head".
- No model of the rest/`RunTest` slot: `Rebase` and `Conflict` (`Runner.tla:140-156`) consume no slot and have no "no slot" outcome, so `FaultSpendsNoAttemptOrBounce` cannot see defect 3.
- `JobCIWait` (`worker.go:40`) and the model's `ciwait` state are never entered by the code (grep); `recover.go:119` has a branch for it.
- `tla/LandEdge.tla` `Pass` is one atomic step; the real `LandPass` is read, read, push, PR, checks, read, merge. The gate-to-merge window (defect 1) and the failed-call outcomes (defect 2, which the model lumps into `absent`) are outside the model. The trace walk (`edge/git/trace_test.go:94`) drives `LandPass` against `git.Fake`, so `Client.MergeGroup`, `Push` lease behaviour and `LsRemote` (defects 8, 12) are bound by functional tests only, which are not the CI trace check the standing practice asks for.
- The model has no outcome for `head_moved`, `missing_head` or `pr_unopenable`; `LandPass` checks `head_moved` only in rung 1 (`land.go:148`), not rung 2 (which merges `req.Heads` regardless of the branch tip).
