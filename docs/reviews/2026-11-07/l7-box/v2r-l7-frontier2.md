## Verdict

**HOLD: the box is not yet sound for the promised cold setup.** The worst gap is that the services a user selects and proves do not determine the provider routes or credentials installed on workers: even `none` installs workers requiring two provider keys, while the supported OpenRouter choice installs no OpenRouter route. This is an independent defensive source review of **43d849e29d0e4568ba6a1348a076a59259639938**, by Stella (Codex), frontier reviewer. All source references below are repository-relative, fixed-base line numbers. Findings are source-derived, not live-fleet reproductions; the walk's sequencing, refusal handling, and bounded probes do not establish that its production readiness predicates prove their advertised facts.

## Defects

1. **serious — The selected services never reach the worker configuration or provider grants.** `verbs/setup_runtime.go:365-378` accepts `none` or names in the probe registry; `verbs/setup_runtime_model_probe.go:15-18` supports DeepSeek and OpenRouter. After saving and proving that selection, production `ServicesReady` returns true and `InstallServices` does nothing (`cmd/nova-sprint/setup_workload.go:81-87`). Every worker nevertheless gets the fixed DeepSeek/Inception routes and keys (`cmd/nova-sprint/setup_workload.go:24-59,105-107`); neither function receives the selected services. The worker setup grants seats through `GrantSeat` (`verbs/setup_runtime.go:546-555`), whose only grant/refresh name is the sprint database password (`verbs/setup_runtime_role_bootstrap.go:99-109`), not the selected provider key. Thus a fresh fleet selecting only OpenRouter can pass step 6, but its installed workers have neither that route nor that key and require two unrelated provider keys; `none` has the same unwanted key requirements. The worker itself checks every configured route's key before model probing (`edge/worker/probe.go:78-81`), so this is not harmless unused configuration. It breaks the one-paste/automatic-grants promise in `docs/SETUP.md:32-36` and the valid `none` choice at `docs/SETUP.md:73-79`. **Counterargument checked:** a previously provisioned fleet with both fixed keys can work, and a failed worker should stop step 7; neither makes the selected service usable on a fresh fleet. No claim is made that an unauthorized secret is exposed. **Repair:** derive worker routes, key names, seat grants and refreshes from the persisted supported-service selection, with an explicit usable meaning for `none`, before marking its setup verified.

2. **serious — The current `up --version` readiness path calls a CLI mode that does not exist.** After matching the installed version and passing `check`, `VersionAdoption.Ready` invokes `run --shadow` and requires success (`verbs/setup_runtime_version.go:50-68`); `RuntimeSetup.Verify` makes this a step-2 requirement when `--version` is supplied (`verbs/setup_runtime.go:109-121`). The registered `run` takes only `--listen` (`verbs/table_coordinate.go:51-53`), and unknown flags are refused (`verbs/flags.go:54-58`). A correctly installed release built from this source cannot pass its own adoption path even when its other checks are green. If the version does not match, `Apply` only refuses with a fleet-install instruction (`verbs/setup_runtime_version.go:121-127`); it does not perform the advertised side-by-side install, swap, three-tick observation or rollback (`docs/PLAYBOOK-COORDINATOR.md:364-366`). **Counterargument checked:** the lower-layer shadow seam exists, but `docs/LAYER-6-RUN.md:587` explicitly says the CLI entry remains pending; `TestVersionAdoptionRequiresCheckAndShadow` fakes successful command execution instead of reaching that parser (`verbs/setup_runtime_version_test.go:17-29`). Installing through nova-fleet is intentional, as its adjacent test confirms; the executable adoption claim still needs reconciliation. **Repair:** connect adoption to an actual non-mutating shadow implementation and its supported release lifecycle, and make the playbook state exactly that lifecycle rather than promising unimplemented swapping and rollback.

3. **serious — Service version verification can prove a different binary from the one the accepted service runs.** An existing run record may use any absolute executable path, and that argv is retained (`cmd/nova-sprint/setup_production.go:715-718,1005-1028`); public dashboard records likewise accept and retain an absolute path (`cmd/nova-sprint/setup_production.go:1181-1202`). However the run/public version checks pass only the machine name, and `checkServiceVersion` always probes `<home>/.local/bin/nova-sprint` locally or remotely (`cmd/nova-sprint/setup_production.go:156,816,856-894`). A retained `/remote/bin/nova-sprint` can therefore be old while an unrelated canonical binary matches, or be correct while the canonical binary is absent. The install/reprobe path installs and reprobes the same canonical location without changing the retained service argv (`cmd/nova-sprint/setup_production.go:823-843`). This defeats the stated check of the version the service “will run” at lines 819-822. **Counterargument checked:** the canonical PATH assumption explains bare `nova-sprint`, but cannot resolve an absolute argv; the repository explicitly tests preserving `/remote/bin/nova-sprint` (`cmd/nova-sprint/setup_production_test.go:177-200`). **Repair:** either normalize/refuse noncanonical service executables or carry the accepted executable through version verification and installation so the proven target is the service target.

4. **serious — Setup reports every worker “dealable” without checking the dealer's hook and hold conditions.** `benchStates` discards all row fields except `State`, and calls bus presence `hooked` (`cmd/nova-sprint/setup_workload.go:119-153`). `SmokeReady` accepts presence, `State == "up"`, and positive configured cores (`cmd/nova-sprint/setup_workload.go:239-256`). The dealer additionally requires `!Held`, a nonempty sprint session and worker/coordinator role (`steps/view.go:311-320`). An ordinary previously held bench, still present/up with positive cores, therefore passes setup's predicate while remaining ineligible for any deal. The resulting “every worker row ... dealable ... VERIFIED” line (`verbs/setup_runtime.go:140-145`) overstates `docs/SETUP.md:82-85`. **Counterargument checked:** deliberately held rows must stay held; the finding does not ask setup to remove an operator hold, and it does not confuse the intentional global stop on fresh setup with row eligibility. Bus presence and a prior successful probe also do not imply that the current sprint hook exists. **Repair:** use the dealer's current row-eligibility predicate and effective capacity when producing readiness, reporting intentional holds honestly instead of asserting all rows are dealable.

5. **minor — The doctor describes a stopped automatic landing as waiting for CI.** `checkLanding` checks run-service availability and stream hold but never `snap.Stopped`; an otherwise readable automatic stream falls through to “run asks every 30s” (`verbs/check_landing.go:38-55,80-84`). `checkRun` means a live chooser, not an unstopped sprint (`verbs/check_sprint.go:153-171`), and the width check only presents stop causes in branches with ready producers (`verbs/check_width.go:41-58`). With merging work, no ready producer or open judgement, a running chooser and a stopped sprint, the doctor can print a green CI-wait line without the required start action. The ticker explicitly plans/applies nothing while stopped (`run/tick.go:143-162`). This contradicts the landing-wait health promise in `docs/CORRECT-USE.md:41` and misdirects someone diagnosing a stall. **Counterargument checked:** already-dispatched external work may finish after stop; choose a merging producer with no outstanding request—the checker never inspects that distinction. **Repair:** report the sprint stop and its reason as the governing landing wait before predicting automatic CI polling, with the coordinator's start instruction.

6. **minor — The embedded recovery playbook instructs coordinators to use rejected commands.** The repeated-finding procedure says to fix the brief with `edit`, and the drop procedure prescribes bare `--waive`, `--relink <other>`, or `--expect <dependant-ids>` (`docs/PLAYBOOK-COORDINATOR.md:293-305`). The verb list has no `edit`, deliberately confirmed by `verbs/core_test.go:66-69`; drop's actual grammar is repeated `--waive <dependant>` / `--relink <dependant>=<card>`, with no `expect` (`verbs/table_coordinate.go:29-31`, `verbs/judge.go:210-226`). These instructions are shipped through `docs/playbooks.go:6-19` and `verbs/help.go:22-27`, not merely an obsolete external note. A newcomer following recovery instructions receives another refusal instead of a usable recovery path. **Counterargument checked:** per-verb help contains the real grammar, but the same binary also prints the contradictory playbook. **Repair:** replace the recovery steps with supported, parser-checked procedures, explicitly deciding how an inactive brief is corrected if `edit` remains absent.

The independent registries at `verbs/setup_runtime_model_probe.go:15-18` and `cmd/nova-sprint/setup_workload.go:24-46` already disagree; unifying their data removes an actual failure mode rather than adding another special case.

- Generate/check executable examples from the same verb table used by help, and reserve prose for decisions and workflow. `TestEveryVerbHasHelp` (`verbs/core_test.go:51-64`) proves help exists, not that embedded playbook commands parse.
