# Layer 7 cold review — Stella

Fixed base: `43d849e29d0e4568ba6a1348a076a59259639938`. Every source line below refers to that base, not a later repair. Report-only independent review; no other reviewers' reports consulted.

## Verdict

HOLD for cold onboarding: the setup walker and its resumability checks have substantial test coverage, but the production adapters and the instructions disagree at important boundaries. The worst defect is that the human's provider selection does not configure the worker services: selecting OpenRouter, DeepSeek alone, or no services still produces workers requiring DeepSeek and Inception credentials, without installing the selected provider grants. Separately, the documented `up --version` path invokes a flag the binary rejects. These are source-established findings, not a claim that a fresh fleet was exercised successfully or unsuccessfully.

## Defects

1. **serious — Provider selection is disconnected from the deployed worker configuration and grants.** `verbs/setup_runtime.go:489-517` saves the selected services and prepares their keys, then passes the selection to `InstallServices`; the production implementations at `cmd/nova-sprint/setup_workload.go:81-87` ignore it entirely. `workerProviderKeys` at lines 24-25 always requires `DEEPSEEK_API_KEY` and `INCEPTION_API_KEY`, and `workerProviders` at line 46 always routes those two providers. In contrast, the accepted key/probe registry at `verbs/setup_runtime_model_probe.go:15-18` contains DeepSeek and OpenRouter. Worker records use those unconditional keys at `cmd/nova-sprint/setup_workload.go:52-59`; the seat grant invoked for each worker (`verbs/setup_runtime.go:551`) grants and refreshes only the database credential (`verbs/setup_runtime_role_bootstrap.go:100-109`). Thus a cold fleet choosing OpenRouter has a proven OpenRouter key but workers configured for unrelated providers; `none` still requests both provider secrets; DeepSeek alone still requires Inception, which the setup registry cannot configure. Existing pre-provisioned seats can mask the problem, and no-bench fleets avoid it, but neither satisfies the fresh-fleet contract at `docs/SETUP.md:32-36`. External nova-secrets failure behavior was not executed; the key/routing/grant mismatch itself is explicit in this source. **Repair:** derive worker routes, required keys and per-seat grants from the durable selected-service configuration, with an explicit supported behavior for `none`.

2. **serious — `up --version` can never complete its shadow verification against this binary's CLI.** Once the installed version matches and `check` succeeds, `VersionAdoption.Ready` calls `run --shadow` at `verbs/setup_runtime_version.go:65`; the actual `run` verb accepts only `--listen` at `verbs/table_coordinate.go:51`, and `verbs/flags.go:54-57` rejects unknown flags. The production store step uses that result at `verbs/setup_runtime.go:109-121`. There is no corresponding shadow dispatch in the inspected main/internal entry paths. A mismatched version refuses earlier; a matching one reaches an unsupported command, so neither yields the promised successful adoption path. `TestVersionAdoptionRequiresCheckAndShadow` at `verbs/setup_runtime_version_test.go:17-25` returns success for arbitrary fake commands and therefore does not validate that this command exists. **Repair:** implement the bounded, non-applying shadow operation and wire the adoption path to its actual interface, or explicitly remove this adoption promise and unsupported call in favor of the intended installer workflow.

3. **serious — The service version gate checks a different executable from an accepted service record.** `selectRunService` accepts arbitrary absolute `argv[0]` at `cmd/nova-sprint/setup_production.go:1005` and returns that argv unchanged at line 1028. Yet the version gate called for that service at lines 155-156 checks only `<home>/.local/bin/nova-sprint` locally (lines 874-875), or `~/.local/bin/nova-sprint` remotely (line 882). An existing valid record pointing at `/remote/bin/nova-sprint` is explicitly supported by `cmd/nova-sprint/setup_production_test.go:192-199`. If that executable is an older build while the canonical install is current, the version gate accepts the current canonical binary while the selected service continues to use the other build. This is not a speculative PATH issue: the accepted absolute path and the probed fixed path differ directly. **Repair:** constrain accepted records to the installation path the gate verifies, or carry the accepted executable through the version probe and installation logic.

4. **minor — Step 8 can declare a held or unhooked worker dealable.** `cmd/nova-sprint/setup_workload.go:149-153` retains only the row's `State`, bus presence and inventory cores; `SmokeReady` at lines 246-256 accepts those alone. Actual dealing requires `!r.Held` and a nonempty sprint session with worker/coordinator role (`steps/view.go:311-320`). A previously held bench that remains bus-present, `up`, and has cores therefore passes setup while it cannot be dealt to; bus presence also does not establish the sprint hook. This contradicts `docs/SETUP.md:82-85`, including on a second setup run where prior row state is normal input. A newly started worker may usually establish its hook, but that does not clear an intentional hold or justify treating bus identity as the hook. **Repair:** use the actual row eligibility predicate for step 8 and report held/missing-session/wrong-role reasons without silently unholding a row.

5. **minor — The suggested dashboard port correction is ignored after the failed attempt stores its answer.** `verbs/setup_runtime.go:474-477` durably saves the dashboard choice before applying/probing the service. An unreachable public endpoint then recommends `--dash public=<machine>:80` at lines 319-322. On retry, `cmd/nova-sprint/setup_production.go:769-775` and `verbs/setup_runtime.go:181-189` prefer the saved choice and ignore the supplied replacement. `verbs/choices.go:93-99` deliberately rejects changed answers, so this is not merely an omitted save call. Opening the original port remains a viable alternative, but the advertised port-change recovery cannot work as written. **Repair:** either provide an explicit, fenced way to replace the saved dashboard choice and use it in the recovery command, or recommend only repairs that preserve the immutable choice.

6. **minor — The coordinator recovery playbook teaches removed or invalid commands.** `docs/PLAYBOOK-COORDINATOR.md:293-294` tells the coordinator to fix a repeated failure with `edit`, while `verbs/core_test.go:68-69` explicitly requires that verb and its help to be unknown. Lines 300-303 teach bare `--waive`, `--relink <other>`, and `drop --expect <dependant-ids>`; the actual help/table at `verbs/table_coordinate.go:29` requires a dependant for each waiver, `dependant=card` for relinking, and has no `expect` flag. A cold coordinator following the recovery recipe receives parser refusals precisely when recovering a stuck card. This is also exposed through the embedded playbook help, not just a detached document. **Repair:** replace these recipes with the supported add/replace and explicit dependant operations, then check playbook examples against the real parser.

## Promise gaps

- `docs/SETUP.md:32-36`: “everything past that point is automatic” and “the seats, the grants, the worker rows and the service rows.” Defect 1 shows the production selection-to-grants-to-worker chain is incomplete; a successful model-list probe is not that chain.
- `docs/PLAYBOOK-COORDINATOR.md:364-366`: “installs the build beside the old” and “swaps back on any overrun, crash or refused tick.” `VersionAdoption.Apply` explicitly refuses and directs the operator to nova-fleet instead (`verbs/setup_runtime_version.go:121-127`); the readiness path is just version/check/shadow subprocesses, with no swap/watch/rollback. The same outdated adoption promise appears in `docs/LAYER-6-RUN.md:299-303`. Defect 2 remains even if the doc is revised to acknowledge external installation.
- `docs/SETUP.md:75`: “except the one the sprint runs on.” `WorkerBenches` intentionally includes every bench (`verbs/setup_runtime.go:50-60`), explicitly tested by `TestWorkerBenchesIncludeTheRunMachineWhenItIsABench` at `verbs/setup_runtime_test.go:209`. This is documentation drift, not a recommendation to remove working capacity.
- `docs/SETUP.md:65-67`: “reads the installed tools' versions” using their help. `InstalledTools` actually reads only nova-config's Go build metadata (`verbs/tools_version.go:15-28`). A consistent nova-tools installation may justify this representative version check, but the text should not promise independent version checks for every tool.
- `docs/SETUP.md:49-60` requires both a cold fresh-fleet walkthrough repeated successfully and the team's own sprint run to completion with its dashboard. This source review and a build/unit/help receipt cannot establish either gate.

## Model vs code

- `tla/Setup.tla:5-21` correctly limits `verified` to observations in the current walk and explicitly excludes a human-input-before-durable-save crash from its asked-once guarantee. The inspected walker restarts and re-probes; I am not treating ordinary world regression after a probe as a model violation.
- The workload correspondence is too weak for its own “dealable” wording: `tla/Setup.tla:23-31` maps world 8 to bus/up/cores, and `cmd/nova-sprint/setup_workload_model_test.go:23-40` exhausts exactly those three booleans per bench. Rows constructed at line 32 do not even carry a sprint session or role. This tests agreement with the weaker predicate, not `steps.View.Open`; it therefore preserves rather than detects defect 4. Include held/session/role eligibility in the mapped state.
- SetupChoices distinguishes no services from configured services, but its actual trace fixture binds only step 6 to the runtime and substitutes world bits for other steps (`verbs/setup_choices_trace_test.go:139-168`), with a fake workload and fake probe. It proves neither selected-provider propagation to production worker records nor provider grants on bench seats. That boundary explains why defect 1 can coexist with a matching choices trace.
- SetupRun's stopped/run-up distinctions are useful for walk ordering; they do not model executable identity, deployment version, the actual `--shadow` parser, or rollback. Setup/SetupChoices similarly abstract readiness into world bits. Their properties cannot discharge defects 2 or 3.
- SetupHandoff and its trace mapping explicitly limit the observation to the child channel/walker/continuation helpers. `cmd/nova-sprint/handoff_trace_test.go:3-5` declares injected lease and credential/schema readiness; the trace calls `runUpChild` through test subprocesses. I found no basis to expand this into production PG exclusion or cold-fleet provisioning proof. No TLC run or historical model-result claim is made here.

## Simplifications

- Use one selected-provider description to produce the supported name, probe endpoint, secret name, worker route and seat grant; the current duplicated registry and worker constants are the source of defect 1.
- Carry a service's executable identity alongside its machine rather than discarding it at the version-check API; this removes the implicit fixed-path assumption behind defect 3.
- Reuse the row eligibility predicate rather than maintaining a second definition of “hooked” and “dealable” in setup. Preserve intentional holds and display their reason.
- Keep immutable saved answers if that is the contract, but make recovery instructions and explicit configuration changes follow that same contract. Do not silently ignore a contradictory recovery flag.
- Derive concise syntax examples from the verb table where possible; keep narrative guidance, but test embedded examples so removed verbs and flags do not survive CLI changes.

## Missing tests

- A bounded adoption test that passes the emitted command through the real verb parser; the existing fake at `verbs/setup_runtime_version_test.go:17-25` validates spelling only by recording it and accepts unsupported commands.
- Production composition tests for `none`, DeepSeek-only and OpenRouter-only, starting with no provider grants and checking the selected worker argv/keys and grant requests. `cmd/nova-sprint/setup_workload_test.go:217` only tests the no-op service step, while its install-workers assertions encode the unconditional provider set.
- A version-gate test with different reported versions for the accepted absolute service path and the canonical install path. The current constructor test explicitly accepts the alternate path without composing it with version verification.
- Step-8 cases for held rows, missing sprint sessions and wrong roles, checked against actual deal eligibility, not only against the model's bus/up/cores projection.
- A persisted public-dashboard choice whose first probe fails, followed by the exact correction advertised in the refusal; assert either an intentional refusal naming the immutable choice or a verified changed endpoint.
- Parser checks for the coordinator playbook's recovery examples, including unknown commands and value-bearing flags; help rendering alone is insufficient.
