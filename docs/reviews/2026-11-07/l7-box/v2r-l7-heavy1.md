# Layer 7: the box a new AI unpacks — Stella (Codex)

Fixed source base: `43d849e29d0e4568ba6a1348a076a59259639938`.
All source citations below refer to that base, not the report commit.
Independent, report-only defensive review; no other review reports read.

## Verdict

HOLD for a cold setup/recovery walkthrough. The command table and the setup walk have useful structure, but the box is not yet a dependable account of the implementation. The worst defect is that a human's selected API services do not determine the worker services or their grants: a fresh fleet can accept a key and verify step 6 while step 7 demands unrelated keys that this setup cannot provision. The upgrade path also calls a flag its own parser refuses. These are source-backed conclusions, not claims of an executed fresh-fleet failure; no live setup, deployment, exploit reproduction, or acceptance run was performed.

## Defects

1. **serious — API-service selection ends before worker configuration and provider grants.** `cmd/nova-sprint/setup_workload.go:24-25,32-46,52-59` always builds OpenCode workers with DeepSeek and Inception routes and both keys. The selected names reach `ServicesReady`/`InstallServices`, but those ignore them and return success (`cmd/nova-sprint/setup_workload.go:81-87`). The supported selector is DeepSeek/OpenRouter only (`verbs/setup_runtime_model_probe.go:15-18`, `verbs/setup_runtime.go:365-378`); it cannot even collect the Inception key every worker requests. After saving a chosen key, step 7 grants only the sprint password (`verbs/setup_runtime.go:546-555`, `verbs/setup_runtime_role_bootstrap.go:100-109`), not the chosen provider key. Thus a fresh fleet with bench seats lacking provider grants, or a human selecting only OpenRouter or `none`, does not get the promised workers from that choice. `docs/SETUP.md:32-36` promises that everything after the one paste, including grants and service rows, is automatic; `docs/SETUP.md:73` expressly accepts `none`. Existing pre-granted DeepSeek/Inception seats can mask this defect, but are an extra prerequisite absent from that promise. The later implementation note explicitly relies on each bench's own provider keys and explains why it avoids granting a name already owned by a seat (`docs/LAYER-6-RUN.md:626-641`): this is a deliberate narrower setup, not evidence that the selected-service promise is fulfilled on a fresh fleet. **Repair:** derive worker routes, key lists and missing encrypted seat grants from one persisted service selection while preserving existing seat-owned keys and make `none` a coherent configuration without requiring unselected provider keys.

2. **serious — `up --version` cannot complete its own advertised adoption check.** Once the installed version matches and `check` succeeds, `VersionAdoption.Ready` invokes `nova-sprint run --shadow` (`verbs/setup_runtime_version.go:59-67`). The run verb accepts only `--listen` (`verbs/table_coordinate.go:51-53`); the common parser refuses every unspecified flag (`verbs/flags.go:54-58`), and the binary has no alternate shadow route (`cmd/nova-sprint/main.go:33-54`, `cmd/nova-sprint/internal.go:17-65`). Therefore even a healthy matching installation reaches an exit-2 usage refusal instead of verifying. For a different installed release, `Apply` merely refuses with a fleet-install recipe (`verbs/setup_runtime_version.go:121-127`). This also contradicts the beside-old install, shadow tick, swap, three-tick observation and automatic rollback promised by `docs/PLAYBOOK-COORDINATOR.md:364-366`. The fleet may install releases safely, but cannot make this build accept `run --shadow` or supply a missing observation/rollback protocol in this adapter. The stub in `verbs/setup_runtime_version_test.go:17-25` returns success for that unparsed command, explaining why its green result would not disprove the defect. **Repair:** implement and integrate a real supported adoption/shadow lifecycle or remove the unsupported call and rewrite the walkthrough to the actual fleet-install and verification contract without claiming rollback.

3. **serious — the card contract promises semantic gate admission that the documented admission path does not provide.** `docs/CARD-CONTRACT.md:49-55` says a permanently red gate is refused at add, a skipping/uncompilable/non-covering gate fails lint, and TEST is system-run red at base and green at head. Later the same contract explicitly says nothing runs at add (`docs/CARD-CONTRACT.md:121-138`). The implementation matches the latter: `cardLint` parses DONE-WHEN and checks routes/retired mechanics/bench names (`verbs/admit_card.go:133-150`); base admission checks paths and carried-head ancestry (`verbs/admit_card.go:198-223`), not gate behavior or negative-control coverage. A syntactically valid gate that does not cover its intended artifact is not distinguishable by those checks. The claim is repeated as an admission guarantee in `docs/PLAYBOOK-COORDINATOR.md:208-214`. This matters because a cold coordinator is told the tool enforces card quality and may treat admission as evidence that semantic gate defects were ruled out. Later worker/read diligence is valuable but is not an add-time refusal. **Repair:** separate automatic syntax/origin admission from coordinator-owned baseline and negative-control evidence, and state exactly which semantic gate guarantees remain manual unless they are implemented as a separate validated admission step.

4. **minor — the dashboard refusal recommends a change that saved answers silently discard.** `verbs/setup_runtime.go:314-322` tells the operator to front an unreachable public board on 80 with `--dash public=<machine>:80`. The dashboard choice is saved before the service is applied/probed (`verbs/setup_runtime.go:462-479`), but subsequent input loses to any saved answer (`verbs/setup_runtime.go:176-191`; the production composer independently does the same at `cmd/nova-sprint/setup_production.go:767-775`). With a saved `public=edge-1`, following the printed fix still probes the old port rather than the now-fronted port 80. `Choices.Save` also refuses changing a stored answer (`verbs/choices.go:91-99`), and the answer survives clear (`verbs/choices_test.go:36-44`). Immutable answers may intentionally prevent accidental drift; that does not make this particular repair command effective. **Repair:** provide a deliberate supported choice-change path, or replace the refusal with a repair that preserves the saved target and explicitly refuse conflicting flags instead of ignoring them.

5. **minor — step 8 reports “dealable” without the dealer's hook/hold conditions.** `benchStates` retains only the store row's state, bus presence and cores (`cmd/nova-sprint/setup_workload.go:119-154`), so `SmokeReady` can return true for a held row or an `up` row with an empty sprint session (`cmd/nova-sprint/setup_workload.go:239-258`). The real dealer's open-row condition additionally requires unheld and hooked (`steps/view.go:315`; `steps/view.go:317-320`). The printed step-8 guarantee says every worker row is hooked, up and dealable (`verbs/setup_runtime.go:144-145`), as does `docs/SETUP.md:82-85`. A bus hook is separate from the sprint session and cannot stand in for it; an operator-held bench remains deliberately undealable. This is an inaccurate verification claim, not evidence that the dealer bypasses holds. **Repair:** share the dealer's eligibility checks for the first-deal probe, reporting held/unhooked rows separately, or narrow the VERIFIED line to the facts actually checked.

6. **minor — recovery instructions still contain commands the shipped CLI cannot run.** The coordinator is told to fix a repeated finding with `edit` (`docs/PLAYBOOK-COORDINATOR.md:293-294`), but `edit` is absent from the closed table and explicitly tested as unknown (`verbs/core_test.go:17-26,68-69`); the same playbook earlier gives add-and-replace as the actual correction route (`docs/PLAYBOOK-COORDINATOR.md:243-246`). Its drop recipe offers `--expect <dependant-ids>` and `--relink <other>` (`docs/PLAYBOOK-COORDINATOR.md:300-303`), while the table has no drop `--expect` and requires `--relink <dependant>=<card>` (`verbs/table_coordinate.go:29-31`). The worker crash/wrap-around recipe repeats bus hook, sprint hook, next (`docs/PLAYBOOK-WORKER.md:96-97`) without the self-unhook required when the persisted session still exists (`verbs/hook.go:68-71`; the correct restart sequence is documented in that file at `verbs/hook.go:14-19`). The worker also must take the brief's named bench lock and SSH to its named test host (`docs/PLAYBOOK-WORKER.md:155-158`), despite the admission lint refusing locks and named-host SSH (`verbs/brief_lint.go:13-18,34-39`). Refusals can rescue some of these paths, but the promised ready-to-copy walkthrough first sends the cold operator into avoidable refusal. **Repair:** replace the retired edit/drop/bench-routing instructions and make restart explicitly branch on the existing sprint hook or include the supported self-unhook step.

7. **minor — the supported store-backed `dash` service never supplies the roster it needs to render row state.** With no `--pull`, `services.Dash` creates a recovering store cache and runs its poller without reading `s.roster` or calling `SetRoster` (`cmd/nova-sprint/services.go:114-125`). `dash.New` starts with an empty roster (`dash/cache.go:44-54`); the setter is the explicit way to supply it (`dash/cache.go:33-39`). With that empty roster, `mapRows` renders every store row as down with default width zero (`dash/shim.go:179-205`), even if a real bench is up, and cannot list configured rows absent from the store. This service is still advertised as serving the board from the store (`verbs/table_coordinate.go:56-57`). The normal run-host board uses `NewFromFeed` with a roster (`dash/run_cache.go:12-29`), so that separate path does not disprove the standalone dash defect; the pull-only public path is unaffected. **Repair:** wire fresh roster observations and errors into the standalone store-backed board, or retire that mode and direct its help to run's existing feed.

## Model vs code

- `Setup` checks ordering, successful verification, durable-answer prompt bounds and restart (`tla/Setup.tla:38-99`); `SetupChoices` refines `none` so it requires no key prompt (`tla/SetupChoices.tla:16-19,92-98`). Those are useful walk-level properties, but `world[7]` is abstract: there is no relation from the selected providers to required worker keys/grants, so they do not cover D1. The actual choice trace uses the real step 6 with a fake workload, while every other step is made true by the test adapter (`verbs/setup_choices_trace_test.go:141-162,201-202`).
- The two-bench binding enumerates bus/up/cores only (`cmd/nova-sprint/setup_workload_model_test.go:23-51`). It does not enumerate Session, Role, Held, provider selection/grants, service-process build identity or harness capabilities. D5 fits that omitted state. `tla/Setup.tla:25-29` also still describes excluding the run machine, whereas `WorkerBenches` now includes it; this is a stale mapping comment, not a demonstrated invariant failure.

The owning doc explicitly records retirement of the old installer/model (`docs/LAYER-6-RUN.md:811-818`); I treated the retained copy as historical scope information. ## Simplifications

- Keep a single provider descriptor for selector, probe endpoint, key name and worker proxy routes, then use it to produce grants and service records; today the two registries disagree (D1). This removes a special case instead of adding more provider-specific branches.
- Generate or mechanically validate runnable playbook command forms against the existing verb/flag table. `help` already derives its verb text from that table (`verbs/help.go:58-72`); prose is where removed mechanics survive (D6).
- Name installation and adoption separately. The local atomic binary replacement has a small concrete contract and tests preserving the old open file and failed-sign behavior (`tools/placebin/place_test.go:40-108`); retaining a larger obsolete shadow/rollback story obscures that good boundary.
- Setup choice reads replay the history (`verbs/choices.go:40-74`) many times in a walk. Consider one explicit bounded read view for a walk's configuration if large-history setup becomes slow; this is a follow-up simplification, not a measured performance defect or a proposal to skip fresh external verification.
