## Verdict

HOLD for the deadline guarantee. The validation, immutable script globals, whole-version fallback and fenced activation are carefully separated, but the process evaluator starts its deadline protection after blocking transport and serialization work and excludes time waiting for another request. That is the worst issue: ordinary concurrent calls need not finish inside the promised budget. This is an independent, report-only source review by Stella (Codex) of fixed base `43d849e29d0e4568ba6a1348a076a59259639938`; every source line below refers to that base. No reproduction, new tests, models, or implementation changes were made.

## Defects

1. **serious — The process engine does not carry the absolute deadline through admission and transport.** `policy/evaluator.go:105` computes the child's budget before `unworded` finishes and before `ev.mu.Lock()` at line 110; `ev.send` is synchronous at lines 114–116, and its `Encode` at line 188 must return before the timeout select at lines 117–130 exists. A second ordinary call on the same engine can wait behind the first beyond its own deadline, including after its caller context expires, then receive the old budget again in the child; serialization/startup time is also outside the parent timer. This breaks L5-5 and L5-16 (`docs/ENFORCED.md:135,146`). Competing explanation: serializing requests is intentional (`policy/evaluator.go:109–111` holds the mutex across each request), and `evalGrace` permits a transport allowance, but neither accounts for a queue of requests or synchronous send preceding the timer. This is a source-proven missing bound, not a measured stall. **Repair:** make admission and transport cancellable against one absolute deadline established before input construction, recompute the remaining child budget at dispatch, and refuse late replies.

2. **minor — A returned consumer-timeout map aliases the local engine's answer cache.** `policy/answer.go:130` clones `BaseRegate` but copies `Timeouts.Consumer` by reference; `policy/validate.go:284–295` builds that map once. The setter closure retains the validated `Timeouts` (`policy/answer.go:112–116`) and is reused without validation on a cache hit (`policy/tick.go:167–182`). Consequently modifying a returned answer's consumer map changes a later answer on unchanged version/inputs in the in-process engine. This contradicts the explicit caller-ownership promise, whose sole exception is Rows (`policy/policy.go:67–71`), and determinism (`docs/LAYER-5-POLICY.md:297–299`). Competing explanation: production `NewEngine` decodes fresh replies through gob, isolating the parent-side map; therefore this is bounded to the local engine and its tests, not an asserted current run-loop corruption. **Repair:** clone `Timeouts.Consumer` in the answer setter just as prices and the catalog are cloned.

3. **minor — Lower-than-wanted candidates reverse the documented name tie-break.** `policy/inputs.go:72,142–145` builds candidates in ascending name order and stable ascending rank order, but `policy/prefer.go:74` reverses the entire lower-rank list, including each rank's equal-rank names. With equally roomy candidates of one rank below the requested rank, the resulting order is descending name; the stable room sort at line 76 preserves it. The promised order is “within a rank, by name” (`docs/LAYER-5-POLICY.md:98`) and the round-5 explanation explicitly relies on the original candidate order (`docs/LAYER-5-POLICY.md:885–886`). Competing explanation: descending rank below the wanted rank is correct; it is the reversal of equal-rank names along with rank groups that is wrong. Scheduling remains legal, so this is ordering, not a tier-safety failure. **Repair:** reverse rank groups while preserving ascending names within each group.

4. **minor — The width-zero/read-count regression no longer constructs its named case.** `policy/break_rowan2_test.go:215–216` replaces the old default width body containing `"ahead": row.width`; the actual default now contains `"ahead": 0` (`policy/default.star:52–53`), so that replacement does nothing. The earlier reads replacement at line 214 still changes the body, satisfying `require.NotEqual` at line 217. Thus the test has two usable rows for two reads, passes at lines 224–225, and never checks the promised refusal when one of those rows has policy work width zero. Competing explanation: `TestColdread3DefectJointCheckIgnoresReadCount` still covers a distinct short rows list, and `jointRows` currently counts work-positive widths; this is lost regression coverage, not evidence that that production check is broken. **Repair:** override width independently and assert the intended width-zero setup plus the specific refusal.

## Promise gaps

- “A tick has one deadline, `TickTime`, from input construction to the last answer” (`docs/ENFORCED.md:135`): the remote call's lock, synchronous send and stale dispatch budget are outside the effective bound; defect 1.
- “Each tick's Answers are the caller's own, except the Rows lists” (`policy/policy.go:69–71`): the new nested consumer-timeout map is not cloned in the local path; defect 2.
- “within a rank, by name” (`docs/LAYER-5-POLICY.md:98`): reversal of the fallback portion reverses names too; defect 3.
- L5-3 lists `TestBreakJointCheckIgnoresTheReadCount` as evidence (`docs/ENFORCED.md:133`), but its width-zero premise is now absent; defect 4.
- The ledger's L5-15 still says an unlisted row “opens one roster judgement” (`docs/ENFORCED.md:145`). The later round-5 prose assigns that judgement to steps alone, and `policy/answer.go:79–89` intentionally creates none for a missing roster row. This is an ownership/documentation mismatch, not an additional policy defect: the integrated steps behavior was outside this layer review.

## Model vs code

Read `tla/Policy.tla`, `tla/Policy.cfg`, `tla/PolicyTrace.tla`, `policy/trace.go` and `policy/trace_test.go`. The model cleanly represents stored activation, previous-active fallback and at-most-one judgement, with failure abstracted into `breaks`; it does not model process admission, request encoding, elapsed time or answer cache ownership. Its atomic Tick therefore cannot establish the transport bound in defect 1 or the map isolation in defect 2.

The new first-set activation is outside the model's current starting boundary: code `policy/verbs.go:122–138` activates when `snap.Policy == 0`, whereas model `Init` already has stored/active version 1 (`tla/Policy.tla:61–67`) and `Set` preserves active (`tla/Policy.tla:74–81`). The trace walk starts with `up` (`policy/trace_test.go:82–86`), so it never binds that startup transition. This is a coverage gap, not a counterexample within the model's stated post-up scope. Data versions likewise are absent from the model but included indiscriminately by `sources` and projected stored membership (`policy/trace.go:78–101`); the current trace fixture avoids data versions. Do not generalize this trace evidence to mixed data/script histories.

`WaitKeepsItsBound` remains layer 3's state and is not projected by policy; this limitation is explicitly acknowledged in `policy/trace.go:29–34`, so no policy defect is inferred from it. No TLC or trace generation was run for this card.

## Simplifications

- Keep one absolute deadline calculation shared by local execution and process dispatch. The current duration handoff and multiple start points make the guarantee harder to audit (defect 1).
- Introduce one internal copy operation for `Timeouts`; it would avoid the partial deep copy becoming stale whenever a nested field is added (`policy/answer.go:130`, `policy/policy.go:114–118`).
- Keep historical Built rounds as evidence, but provide a compact current contract: the opening “not built” (`docs/LAYER-5-POLICY.md:3`), old load budget (`:347–349`) and original model description (`:314–319`) require reconciliation with later rounds. These are documentation maintenance opportunities, not extra runtime findings.
- The custom Go `prefer` optimization is justified by the shared candidate-set load shape; no blanket removal is recommended. Preserve the simple rank/name ordering contract when repairing its fallback grouping.
