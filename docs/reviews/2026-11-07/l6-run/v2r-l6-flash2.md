## Verdict

The layer is not sound against its documented delivery and freshness contracts at base `43d849e29d0e4568ba6a1348a076a59259639938`. The worst issue is that observing a clear leaves old pending notifications in memory, so run can send stale instructions after the epoch changes without the required cancellation summary. This is a bounded cold review, not a complete audit of the layer.

## Defects

1. **Serious — clear does not cancel queued notices.** `run/tick.go:113`–`123` folds the new epoch and clears inbox/refusals/inflight but leaves `t.push` intact; `run/push.go:130`–`149` then sends that old queue using the current epoch for the cursor. A failed send before clear followed by a successful send afterward therefore delivers old-epoch instructions and no clear summary, contrary to `docs/LAYER-6-RUN.md:582`. Repair by processing clear in event order, cancelling old pending notices and producing the specified per-recipient summary before advancing the cursor, including on cold catch-up.
2. **Serious — restart renders historical events from the latest snapshot.** `run/push.go:89`–`106` supplies the same cold snapshot for every replayed event; `run/notices.go:37`–`45` computes terminal stream notices from that snapshot. If a stream became terminal, then acquired a new nonterminal producer before restart, the earlier terminal event is no longer reported as terminal; conversely, several earlier terminal transitions can all be rendered as terminal based on the later state. Repair by reconstructing each recipient's cursor state and folding each event before rendering it, as required by `docs/LAYER-6-RUN.md:582`.
3. **Serious — a failed fold refreshes the dashboard.** `run/serve.go:151`–`168` publishes the snapshot with the current tick time even when `Fold` or `Tick` returns a non-lock error. A persistent event-read failure can thus make an old or partially folded view appear fresh, hiding the stale alarm; the contract at `docs/LAYER-6-RUN.md:583` says failed folds do not refresh the clock. Repair by publishing only after a complete successful fold and retaining the last successful timestamp otherwise.
4. **Serious — failed preemption stop is never retried.** `steps/preempt.go:57`–`64` attaches a stop to an accepted preemption; `run/tick.go:305`–`312` records it in flight before `run/edges.go:101`–`107` sends it. On a bus error the goroutine logs and returns without a result, while `run/tick.go:291`–`297` retires in-flight requests only on consumed results; the stop remains in flight indefinitely and the old runner can continue after preemption. Repair by retaining and retrying failed stop delivery with a bounded, observable retry policy and retiring only on a confirmed acknowledgement.
5. **Minor — the run-host stale monitor is not started.** `run/serve.go:69`–`81` starts the heads watcher and HTTP server but no freshness monitor, while `dash/run_cache.go:62`–`68` exposes `CheckFreshness` and `dash/run_cache_test.go:23`–`28` calls it directly. If the run loop stalls and nobody visits `/healthz`, no stale alarm is raised despite `docs/LAYER-6-RUN.md:583`; start a clock-driven independent monitor for the run-fed cache.
6. **Minor — judgement group metadata is discarded.** `run/notices.go:111`–`117` attaches a group to each notice, but `run/push.go:158`–`175` only concatenates lines and never reads `Group`; multiple grouped judgements are not represented as the group/size/IDs and group command promised by `docs/LAYER-6-RUN.md:365`–`375`. Repair by constructing the documented group summary and command from the grouped committed judgements, reconciling it with the later one-envelope-per-recipient rule.

## Promise gaps

- `docs/LAYER-6-RUN.md:582`: “Once Clear is seen, old-epoch pending notices are cancelled” — `run/tick.go:122`–`123` does not clear the pusher queue, and `run/push.go:138` sends it.
- `docs/LAYER-6-RUN.md:582`: “It renders the notice at the event's sequence, not from the latest state” — catch-up calls `Observe(e, cold)` at `run/push.go:104`–`106`.
- `docs/LAYER-6-RUN.md:583`: “a failed fold does not refresh the clock” — `run/serve.go:151`–`168` publishes with `At: start` even on an error other than lock loss.
- `docs/LAYER-6-RUN.md:583`: “The no-viewer monitor raises the existing stale alarm” — `run/serve.go:69`–`81` never starts a monitor, and the unit test invokes `CheckFreshness` manually.

## Model vs code

`tla/RunClear.tla:10`–`14`, `60`–`67` suppresses old backlog after observing the new epoch and includes a clear summary; `run/tick.go:113`–`123` and `run/push.go:124`–`149` retain and send queued notices instead. The model explicitly allows a send prepared before clear to race with clear; the finding is the distinct case where clear has already been folded. The run trace records `DeliverEdge` as soon as the stop request is returned (`run/run_trace_test.go:562`–`568`), without driving `Edges.stop`, so it does not cover the failed-delivery path above. I did not run TLC or establish trace conformance for this base.
