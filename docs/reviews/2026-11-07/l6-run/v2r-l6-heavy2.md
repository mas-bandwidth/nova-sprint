## Verdict

**HOLD for the reviewed runtime paths.** Cold defensive source review by Stella (Codex), fixed base `43d849e29d0e4568ba6a1348a076a59259639938`. The strongest problem is that every notification recipient is serviced synchronously on the chooser's tick path, outside its deadline, so an ordinary slow bus can delay scheduling and board publication across many seconds. The report identifies six source-supported defects; it does not certify all of layer 6. No code, tests, models, live services, or hostile-input probes were changed or executed. All file/line citations below refer to that fixed base.

## Defects

1. **serious — Push serializes external sends on the tick, outside its budget.** `run/serve.go:158-168` cancels the tick deadline and then calls `Ticker.Push` with the service context before publishing the board; `run/push.go:130-145` sends recipients sequentially and persists a cursor for each. The real transport permits five seconds per send (`edge/bus/bus.go:19-21,74-75`), so multiple ordinarily slow recipients accumulate delay on the only scheduler goroutine (`run/serve.go:83-93`). This contradicts the separate pusher and off-tick cost claims at `docs/LAYER-6-RUN.md:67-73,91-94`, with scheduling, lock-loss detection, and dashboard updates all delayed together. **Competing explanation:** sends are bounded individually, so this is not a claim of an unbounded transport call; the defect is the sum of those bounds on the tick and exclusion from its deadline. **Repair:** move committed notification delivery and cursor persistence to a separate worker over a safe committed feed, keeping per-recipient ordering and at-least-once retries.

2. **serious — A failed event fold is published as fresh, healthy dashboard state.** `run/serve.go:151-168` proceeds to `board.Publish` for every error except `ErrLockLost`, including `Ticker.Fold`'s store-read error (`run/tick.go:106-108`). `dash/run_cache.go:48-55` clears the cache error/alarm and assigns the new timestamp, and `dash/server.go:77-91` derives success and data age from that published view. With a healthy roster but repeated failed Events reads, the board can repeatedly show the old sprint state at near-zero age, including an obsolete RUNNING/STOPPED value. This directly contradicts `docs/LAYER-6-RUN.md:583`: “a failed fold does not refresh the clock.” **Competing explanation:** the tick log retains its error, but the board has no fold-error field and its freshness is independently reset; logging does not preserve the board's promised semantics. **Repair:** publish only a completed fold, and retain the last successful fold timestamp plus an explicit store-read error when folding fails.

3. **serious — Cold start forgets the previous active policy.** `run/tick.go:82-91` initializes a ticker from the snapshot but leaves `prev` at zero; only subsequent folded activation events update it (`run/tick.go:118-120`). `run/asker.go:31-44` consequently passes no previous version after restart, even when an earlier active version exists in the log. If the current active version fails on a question, the engine receives active plus built-in instead of active, previous active, built-in. This violates the fallback order in `docs/ENFORCED.md:134` (L5-4), and makes the same persisted sprint choose different fallback limits/decisions across restart. **Competing explanation:** updating PrevOf incrementally is the intended efficient steady-state path (`docs/LAYER-5-POLICY.md:472-473`); it does not recover activations preceding the cold snapshot. The deliberate no-deal gate on a failed active policy limits dealing, but does not restore the missing fallback for the rest of the tick or initial limits. **Repair:** recover the previous active version once at cold start, then continue updating it incrementally, and reset/recover it at epoch transitions.

4. **serious — Observing Clear does not cancel old pending pushes or emit the cancellation summary.** `run/tick.go:115-124` observes every event and resets inbox/refusals/in-flight requests at an epoch change, but preserves the pusher. `run/push.go:58-71` only appends notices, and `run/push.go:124-151` later sends queued entries irrespective of their original epoch or the recipient's current subscription. Thus notices that failed before a clear remain eligible after the new epoch has already been observed; no clear summary is constructed. This differs from both `docs/LAYER-6-RUN.md:582` and `tla/tla/RunClear.tla:10-20`. **Competing explanation:** the model explicitly allows an old send when Clear races an already prepared send; this finding concerns the stronger, separate case where Fold has observed Clear before Push starts. Epoch-bearing deal commands help refuse stale mutations, but do not cancel obsolete messages or provide the promised accounting. **Repair:** tag retained notices by epoch and cancel the observed old backlog with the modeled bounded summary before advancing a new-epoch push cursor.

5. **minor — Cold catch-up changes or loses historical stream-completion notices.** `run/push.go:104-106` renders every historical event against the final cold snapshot. Terminal detection is event-local (`run/notices.go:41-44`) but `terminalNotice` counts all producers in the supplied snapshot (`run/notices.go:156-168`). If a stream completed, then received another unfinished producer before restart, its undelivered completion notice is suppressed; if several terminal transitions preceded restart and the stream is now complete, earlier transitions each produce a duplicate summary of the final totals rather than their historical state. This contradicts the explicit event-sequence rendering claim at `docs/LAYER-6-RUN.md:582`. **Competing explanation:** at-least-once delivery permits resending the same historical notice, but not replacing it with later totals or suppressing a previously due notice because later work was added. No store mutation or landing safety failure is claimed. **Repair:** reconstruct the state at the catch-up cursor once and fold forward while rendering each event against its own after-state.

6. **minor — Roster-read failure bypasses the chooser health check entirely.** At `run/serve.go:151-155`, a failed roster read calls `Ticker.Fold` directly, bypassing the health check in `Ticker.Tick` (`run/tick.go:152-153`); `Fold` itself has none (`run/tick.go:104-129`). The loop then sends pushes and writes push cursors (`run/serve.go:163`, `run/push.go:143-145`) and only exits on an error classified as lock loss. If the lock session or hook fails during an ongoing roster outage, run never consults it on those ticks and can continue delivering indefinitely until the roster recovers or the service stops. **Competing explanation:** no scheduler move is planned in this branch, so this is not proof of concurrent card scheduling; it is failure to detect lock loss/exit and a push ownership discrepancy. This is beyond the accepted short health-check/Apply race documented at `docs/LAYER-6-RUN.md:577`. **Repair:** run the health check unconditionally before either planning or fold-only degraded operation and stop push preparation after observed loss.

## Promise gaps

- “A goroutine beside the tick” (`docs/LAYER-6-RUN.md:67`): delivery is inline after cancellation of the deadline; defect 1.
- “a failed fold does not refresh the clock” (`docs/LAYER-6-RUN.md:583`): the enclosing loop unconditionally publishes except on lock loss; defect 2.
- “active, previous active and the built-in” (`docs/ENFORCED.md:134`): only post-start activations populate the runtime's previous version; defect 3.
- “Once Clear is seen, old-epoch pending notices are cancelled” (`docs/LAYER-6-RUN.md:582`): only steps' volatile state is cleared, not the push queue; defect 4.
- “It renders the notice at the event's sequence, not from the latest state” (`docs/LAYER-6-RUN.md:582`): CatchUp supplies the same latest snapshot for every historical event; defect 5.
- “Check the lock connection is alive” (`docs/LAYER-6-RUN.md:53`): the roster-error branch skips it; defect 6.

The document mixes a historical foundation checkpoint with later integration notes. I treated the specific above promises as requirements because no later inspected ruling revokes them, while explicitly accepting the weaker chooser guarantee and the known stale land-request race in `docs/LANDING.md` rather than rediscovering either as a new defect.

## Model vs code

`Run.tla` explicitly permits a check/use lock-loss window and assumes eventual successful transport; it does not establish the one-second/two-tick performance bar. Its `PreparePush` requires an active chooser (`tla/Run.tla:274-275`), whereas the roster-failure branch can prepare and send without a health observation. `tla/RunClear.tla:10-20` distinguishes a send racing Clear from suppression after Clear is observed; the latter behavior is absent from the runtime pusher. The runtime source trace fixture deliberately restricts scheduling order and push timing (`run/run_trace_test.go:15-38`), so passing those traces cannot establish these unrepresented combinations or the wall-clock bound.

The inspected Setup and SetupChoices models explicitly scope “asked once” to a durably saved answer and verification to this walk's observed probes, not simultaneous distributed truth (`tla/Setup.tla:5-18`). I found no new defect in the inspected outer `verbs/setup.go` verify/act/reverify and handoff flow from those distinctions alone. Full production setup adapters were not exhaustively reviewed, and no TLC run was made by this reviewer.

## Simplifications

The separate implementations of historical catch-up and live-fold notification rendering should share one event-state advancement path; this would reduce the semantic split behind defect 5. A single unconditional health/fold/publication lifecycle would reduce the special branch behind defects 2 and 6. Keep the pusher's existing recipient batching and bounded envelope (`run/push.go:158-178`) while moving its I/O out of the tick; a separate implementation of every notification kind is unnecessary.
