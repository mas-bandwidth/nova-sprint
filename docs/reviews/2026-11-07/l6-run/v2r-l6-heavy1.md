## Verdict

HOLD on fixed base `43d849e29d0e4568ba6a1348a076a59259639938`. The core uses sensible generation fences, receipt replay, a dedicated chooser session and committed event images, but the runtime wiring does not keep several explicit delivery and observability promises. The worst defect is that observing Clear does not cancel old notification backlog or emit its promised summary, contrary to both the documented built behavior and `RunClear.tla`. This is an independent, report-only defensive source review by Stella (Codex); no other review reports were read, and no code, new tests, models or reproduction programs were created. Coverage is focused rather than a complete-file certification: the layer inventory is over 32,000 Go lines including tests, before page assets and model evidence. All citations below refer to the fixed base, not this report's commit.

## Defects

1. **serious — Clear leaves old notification backlog active and emits no cancellation summary.** `run/tick.go:113-124` detects an epoch change but clears only inbox/refusals/inflight; `run/push.go:58-73` appends notices with no epoch filtering, and `run/notices.go:16-54` has no Clear handling. Thus an earlier failed send can remain queued when a later fold observes Clear, and `run/push.go:138-149` sends it and advances its cursor using the new epoch supplied by `run/tick.go:60-61`. Cold catch-up also feeds every historical event to Observe without an old-epoch check (`run/push.go:96-109`). This contradicts the explicit built cancellation behavior at `docs/LAYER-6-RUN.md:582` and the scan rule at `tla/RunClear.tla:60-67`. **Competing explanation checked:** Clear refuses live consumers (`verbs/operate.go:227-235`), but pending withdraw, landing and judgement notices can exist after consumers become final; the refusal does not empty the pusher. Epoch-bearing commands protect later mutations, but do not cancel obsolete instructions or communicate the promised summary. **Repair:** track pending notices by epoch, suppress old backlog once Clear is observed, and acknowledge it only through the confirmed Clear summary.

2. **serious — Release adoption calls a shadow command that this binary rejects.** `verbs/setup_runtime_version.go:62-66` requires successful `run --shadow`; production wires this adapter at `cmd/nova-sprint/setup_production.go:81`, and setup invokes it for an already-ready store with `--version` at `verbs/setup_runtime.go:113-121`. However `verbs/table_coordinate.go:51` declares only `listen=` for run, and `verbs/flags.go:54-57` refuses any undeclared flag before dispatch. A matching installed release therefore cannot pass this adoption check even when its check succeeds. **Competing explanation checked:** the newer policy that nova-fleet owns installation is explicit (`verbs/setup_runtime_version.go:121-127`); it does not remove the still-executed shadow check. **Repair:** implement and wire the read-only shadow entry point, or replace the adoption prerequisite with an implemented validation contract and update its callers/docs together.

3. **serious — Failed folds refresh the dashboard as if the store were fresh.** `run/serve.go:151-158` keeps a Fold/Tick error, but for every error except `ErrLockLost` still calls Publish at `run/serve.go:159-170` with the current tick's time and retained snapshot. `dash/run_cache.go:48-55` clears the cache error/alarm and remaps that snapshot as a fresh view; `dash/server.go:153-163` judges health by the refreshed time. If Events repeatedly fails while roster reads succeed, the sequence can stay unchanged indefinitely while data age remains small and health remains 200. This violates the explicit completed-fold-only statement at `docs/LAYER-6-RUN.md:583`. **Competing explanation checked:** an idle successful fold is legitimately fresh at the same sequence; the distinguishing evidence here is the non-nil fold error, which is logged but never passed to the board. **Repair:** publish fresh state only after a completed fold, retaining the last successful timestamp and exposing the read failure otherwise.

4. **serious — Bus sends serialize the tick and dashboard behind recipient latency.** `run/serve.go:163-168` calls Push directly after cancelling the planning deadline and before publishing the board. `run/push.go:130-147` sends to recipients sequentially and saves each cursor before the next recipient. Production bus sends have a five-second default timeout (`edge/bus/bus.go:20,47-51,74-75`); several slow recipients can therefore delay subsequent ticks and board updates by the sum of their send durations. This is a structural violation of the off-tick pusher promised at `docs/LAYER-6-RUN.md:67-73,91-95`, not a measured p99 claim. **Competing explanation checked:** sends are outside the store writer lock, which is good, and each individual bus call is bounded; neither property isolates tick latency. **Repair:** move delivery/cursor work to an owned, cancellation-aware worker with serialized queue ownership and a bounded handoff from the event fold.

5. **serious — Standalone store-backed dashboard never receives a roster.** `cmd/nova-sprint/services.go:117-125` constructs NewRecovering and runs Cache.Run without reading or setting a roster. The cache starts with a zero roster (`dash/cache.go:51-52`), and the only setter is `dash/cache.go:36-40`; no call to SetRoster exists in the reviewed command/dashboard packages. Mapping an otherwise-up row absent from that roster falls through to `Status: "down"` with width zero (`dash/shim.go:179-205`), and normal kin workers land in Fleet rather than Friends (`dash/shim.go:202-205,226-230`). Thus the documented standalone `nova-sprint dash --listen` mode can show a fresh store with every active worker down. **Competing explanation checked:** this fallback is useful for an actually unknown row, and run-fed boards do supply a roster (`run/serve.go:168`); the standalone public command does not. **Repair:** refresh the authoritative roster and its failure status alongside each standalone fold, using the same advertised-row mapping as the run-fed board.

6. **minor — Cold catch-up renders terminal stream facts from the latest snapshot.** `run/push.go:104-106` passes the same cold snapshot for every historical event; terminal notices then inspect all producers in that supplied snapshot (`run/notices.go:43-46,156-169`). If a stream completed and another producer was later added before restart, its historical completion notice is suppressed; if multiple landing events are replayed into an all-terminal cold snapshot, each can claim the stream is done. This contradicts event-sequence rendering at `docs/LAYER-6-RUN.md:582`. **Competing explanation checked:** individual LANDED notices use event images (`run/notices.go:37-39`) and remain recoverable; the error concerns the stream-level terminal summary, not those individual receipts. **Repair:** reconstruct the state at the recipient's cursor and fold catch-up events in order before deriving terminal summaries.

7. **minor — Roster failure bypasses the chooser health check entirely.** With a roster read error, `run/serve.go:151-152` calls Fold directly instead of Tick, while the health check lives in `run/tick.go:152-154`; Fold itself only reads Events (`run/tick.go:104-129`). Push still runs (`run/serve.go:163`). A failed roster plus a dead chooser session/hook therefore prevents the promised lock-loss exit for as long as roster reads fail. **Competing explanation checked:** this branch applies no scheduler ops, so it does not by itself prove stale tick writes; the bounded claim is failure to observe/exit on loss and continued push/cursor activity. The documented non-atomic health-check window (`tla/Run.tla:12-18`) is a different, accepted limitation. **Repair:** check chooser health on every loop iteration before selecting either the normal planning path or the fold-only fallback.

## Promise gaps

- “Once Clear is seen, old-epoch pending notices are cancelled and the recipient gets” the cancellation summary (`docs/LAYER-6-RUN.md:582`): neither cancellation nor summary exists in the current pusher (defect 1).
- “`--shadow` plans one tick ... applies and sends nothing” (`docs/LAYER-6-RUN.md:85-86`): public parsing refuses the flag, while release adoption requires it (defect 2).
- “a failed fold does not refresh the clock” (`docs/LAYER-6-RUN.md:583`): loop publication ignores fold failure (defect 3).
- “A goroutine beside the tick” (`docs/LAYER-6-RUN.md:67`) and “pushes off the tick's path” (`docs/LAYER-6-RUN.md:91-92`): sends are synchronous in the tick (defect 4).
- “Either way ... the copy advances every second” with the standalone log follower (`docs/LAYER-6-RUN.md:326-330`): its store copy advances, but authoritative row facts are never provided (defect 5).
- “It renders the notice at the event's sequence, not from the latest state” (`docs/LAYER-6-RUN.md:582`): catch-up reuses cold state (defect 6).
- “Check the lock connection is alive; if not ... exit 2” (`docs/LAYER-6-RUN.md:53`): roster-error fallback omits this check (defect 7).
- `docs/ENFORCED.md` was inspected as the supplied contract ledger; it has no layer-6 rule table. Its layer-3 and layer-5 bindings are not evidence that these layer-6 production adapters are covered.

## Model vs code

`tla/RunClear.tla:10-25,60-87` explicitly separates a Clear racing an already-prepared send (allowed) from a scan that has observed the newer epoch (old backlog suppressed). Defect 1 is the latter case; it does not demand the deliberately false stronger invariant `NoOldSendAfterClear` (`tla/RunClear.tla:118-122`). The main Run model's push prefix includes all modeled events (`tla/Run.tla:272-295`), whereas code queues only relevant notices and advances only to the last such notice (`run/push.go:63-73,143-147`). That abstraction does not establish historical summary correctness or Clear coverage.

The weaker chooser ruling is expressly recorded at `tla/Run.tla:12-18`: a check and later Apply cannot be atomic on separate sessions. I do not report that known window as a new defect. Generation and Running conditions are visibly applied (`run/tick.go:244-264`), and stop-before-planning is present (`run/tick.go:161-163`). The time-free model also explicitly does not prove the one-second/two-tick load bar (`tla/Run.tla:38-43`), so a passing model would not dismiss defect 4.

`tla/Setup.tla:5-20,49-83` models re-verification from step 1 and durable answers; `verbs/setup.go:178-199,295-318` implements that broad walk. The model abstracts external probes as truthful world facts and does not exercise the actual command parser used by the release adapter. The mock adoption test therefore cannot bind the missing shadow command to the model. No TLC run or trace-refinement result is claimed by this reviewer.

## Simplifications

- Keep one delivery state machine for live folding, restart catch-up and Clear, rather than reconstructing different notice semantics in each route (`run/push.go:58-111`). A cursor should name the fully scanned/covered prefix even when many scanned events need no message; currently an idle recipient's cursor can remain far behind and restart revisits irrelevant history.
- Keep roster/snapshot freshness and failure as one feed contract for both serving modes (`dash/run_cache.go:12-23` versus `dash/cache.go:30-40` and `cmd/nova-sprint/services.go:117-125`), reducing the separate setup that caused defect 5.
- Make the public verb table the source of executable internal command contracts. The version adapter's literal shadow invocation and its permissive mock diverged from that table (`verbs/setup_runtime_version_test.go:17-25`).
- Consolidate historical checkpoint prose into a clear current contract: the Built foundation still describes provisional seams and a pusher behavior absent from the fixed-base implementation (`docs/LAYER-6-RUN.md:574-593`). This is a maintenance suggestion, not a substitute for repairing the still-promised behavior.
