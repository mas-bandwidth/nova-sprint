# Layer 6 cold review — Stella

Fixed base: `43d849e29d0e4568ba6a1348a076a59259639938`. All source line references below name that base, not this report commit. This is an independent defensive source review; no other review reports were consulted, no reproduction was constructed, and no code or tests were changed.

## Verdict

HOLD for the inspected integration paths, with incomplete whole-layer coverage disclosed below. The worst defect is that independent landing goroutines for streams sharing a repository also share a mutable Git checkout: serialization by stream does not protect the checkout. Other serious defects let stale store state appear fresh, change policy fallback after restart, and block version adoption on an unsupported command. The notification implementation also lacks two behaviors described as built; one is explicitly acknowledged as owed by the current model mapping. These are source conclusions, not claims of observed production incidents or exhaustive acceptance results.

## Defects

1. **Serious — concurrent streams mutate the same landing checkout.** `run/edges.go:81-86` starts one goroutine per landing, while `run/edges.go:271-278` derives its directory solely from the repository URL. `steps/land.go:124-138,168-169` excludes an in-flight request only for the same stream. Consequently, two streams of one repository can enter `MergeGroup` on the same worktree. That routine changes the detached checkout, merges, reads `HEAD`, and may abort/reset the checkout (`edge/git/git.go:263-307,309-324`), without a lock spanning that sequence. The consequence is interference between otherwise valid landing requests: false conflicts/faults and a merge result whose working state was changed by the other request. Git's individual index locks and the remote branch lease do not serialize this multi-command local transaction. No contaminated remote landing was demonstrated. **Repair:** isolate mutable landing worktrees by request or serialize the complete checkout-mutating pass per repository.

2. **Serious — failed event folds refresh dashboard health.** `run/tick.go:104-109` returns a store read error, but `run/serve.go:151-171` skips publishing only for `ErrLockLost`; other failures publish the ticker's retained snapshot with the current tick's `start`. `dash/run_cache.go:37-55` accepts an equal sequence and resets `at`, `err`, and the alarm, and `dash/server.go:153-163` reports healthy solely from the age of `at`. With working roster reads but repeated failed event reads, obsolete cards and control state can remain apparently fresh indefinitely. Equal-sequence successful idle folds legitimately need freshness updates; the defect is losing the fold's success/failure distinction, not accepting equal sequence numbers. **Repair:** publish freshness only after a completed successful fold, preserving the last successful timestamp and an explicit read failure otherwise.

3. **Serious — restarting run discards the previous active policy.** `run/tick.go:82-91` constructs a ticker with zero `prev`; `run/tick.go:106-119` discovers previous activation only among events after the cold snapshot. `run/serve.go:99-107` seeds policy and catches up notices without restoring that field, and `run/asker.go:31-47` consequently omits `Versions.Prev`. A policy that worked when activated but now fails for changed facts falls back to the built-in after restart, whereas the same long-running process can use the previous active version (`policy/answer.go:25-35`). The argument-free verb adapter independently supplies only Active (`verbs/apply.go:64-76`). This can change limits, timeouts, and non-deal decisions. Counterargument checked: `run/asker.go:75-95` deliberately blocks dealing whenever the active version fails; this finding does not claim fallback permits new deals. **Repair:** recover the previous activation at the cold snapshot sequence once and share the same version-selection semantics with verbs, then maintain it incrementally.

4. **Serious — notification I/O serializes and delays the tick and board.** `run/serve.go:158-168` cancels the tick budget and then synchronously calls `Push` with the service context before publishing the board. `run/push.go:124-149` sends to recipients serially and writes each cursor synchronously. The real bus command has a five-second default timeout (`edge/bus/bus.go:20,50,74`), so ordinary unavailable/slow recipients can consume multiple tick intervals. This is bounded per bus call, not an assertion of an infinite wait or a measured p99 failure; there is no independent tick progress during those waits. **Repair:** move notification delivery to a bounded worker with explicit ownership of queued committed notices and cursors so it cannot delay folding or dashboard publication.

5. **Serious — version adoption requires a CLI flag absent from the CLI.** Once the installed version matches and `check` succeeds, `VersionAdoption.Ready` runs `run --shadow` and refuses on its failure (`verbs/setup_runtime_version.go:59-68`). The run verb allows only `listen=` (`verbs/table_coordinate.go:51`); the common parser rejects an unknown flag (`verbs/flags.go:54-57`). Thus this base cannot complete its own adoption verification even when installation and check succeeded. The design's older promise of shadow support is weakened by its later admission that the CLI entry is pending (`docs/LAYER-6-RUN.md:587`), but that does not make calling it from production adoption valid. **Repair:** implement and wire the promised side-effect-free shadow command before making it a required adoption check.

6. **Serious — Clear leaves old pending notifications deliverable.** `run/tick.go:113-124` folds Clear but drops only inbox/refused/inflight state. `run/push.go:58-71,124-149` retains queued notices without epoch suppression and later saves their cursor using the current epoch. `run/notices.go:16-54` has no Clear summary path. Old DEAL/WITHDRAWN instructions can therefore arrive after the process has already observed Clear; cold catch-up likewise does not suppress prior-epoch notices (`run/push.go:104-106`). DEAL commands include epoch arguments (`run/notices.go:72-91`), which mitigates stale store mutations but does not satisfy notification cancellation or prevent obsolete instructions from reaching workers. This is an acknowledged implementation gap, not a newly demonstrated race: `tla/RunTrace-MAPPING.md:198-199` expressly calls it owed. **Repair:** make Clear cancel pending old-epoch notifications and durably account for the promised bounded summary before advancing the recipient cursor.

7. **Minor — cold catch-up renders historical stream notices from the final snapshot.** `run/push.go:104-106` passes the same cold snapshot for every event, whereas `run/notices.go:41-46,156-188` decides stream completion and counts from that supplied snapshot. Historical producer terminal events can each generate the same final completion summary; conversely, subsequently added nonterminal work can suppress a completion that existed at the original event. Event before/after images correctly identify the changed producer, but are insufficient to supply the other producers' historical state. **Repair:** reconstruct the state at the recipient's historical position once and fold forward while rendering each event at its own sequence.

8. **Minor — the standalone store-backed dashboard never receives a roster.** `cmd/nova-sprint/services.go:106-125` constructs and polls `dash.NewRecovering` without a roster source or `SetRoster`; `dash/cache.go:30-39,44-53` initializes none. Consequently `dash/shim.go:180-205` treats store rows as unknown/down, with no advertised width, and cannot include roster-only machines. The run-fed and public pull paths have different wiring and are not implicated. **Repair:** supply current roster observations and errors to the standalone cache alongside each successful store fold, or explicitly remove that advertised serving mode.

## Promise gaps

- **Serious, D2:** “a failed fold does not refresh the clock” (`docs/LAYER-6-RUN.md:583`) is contradicted by `run/serve.go:168` and `dash/run_cache.go:50`; repair is to preserve last successful fold freshness.
- **Serious, D3:** “A tick is answered by the first passing version of active, previous active and the built-in” (`docs/ENFORCED.md:134`, L5-4) requires retaining the previous active candidate; `run/tick.go:90-91` loses it across restart; repair is snapshot-consistent cold recovery.
- **Serious, D4:** “A goroutine beside the tick” (`docs/LAYER-6-RUN.md:67`) is instead the synchronous `run/serve.go:163` call; repair is independent bounded delivery with clear state ownership.
- **Serious, D5:** “plans one tick on the live store without the lock, applies and sends nothing” (`docs/LAYER-6-RUN.md:85-86`) has no accepted CLI flag (`verbs/table_coordinate.go:51`); repair is to wire the no-write planner before adoption invokes it.
- **Serious, D6:** “Once Clear is seen, old-epoch pending notices are cancelled” (`docs/LAYER-6-RUN.md:582`) is not implemented by `run/tick.go:122-124`; repair is epoch-aware cancellation and summary accounting.
- **Minor, D7:** “It renders the notice at the event's sequence, not from the latest state” (`docs/LAYER-6-RUN.md:582`) conflicts with `run/push.go:106`; repair is historical fold-based rendering.
- **Minor, D8:** “a row's pill is down if down, else held if held, else up” (`docs/LAYER-6-RUN.md:338-339`) is unattainable for the documented standalone serving path without its roster (`cmd/nova-sprint/services.go:118-125`); repair is complete standalone feed wiring.

## Simplifications

- **Minor, D3:** centralize snapshot-consistent policy version selection instead of keeping separate incomplete adapters in `run/asker.go:31-47` and `verbs/apply.go:64-76`; `policy/verbs.go:303-328` already defines the recovery semantics. Preserve incremental operation after recovery rather than adding an event-log scan every tick.
- **Minor, D2/D8:** reduce the separate feed/standalone freshness and roster conventions (`dash/run_cache.go:12-22`, `dash/cache.go:30-39`) to one explicit successful-fold-plus-roster observation boundary; it would make the two missing integrations visible in the types and tests.
