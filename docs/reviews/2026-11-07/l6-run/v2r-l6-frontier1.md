# Layer 6 cold review — Stella

Fixed base: `43d849e29d0e4568ba6a1348a076a59259639938`. All source lines refer to that base. Report-only defensive review; no production changes, new tests/models, or reproductions. Reviewer: Stella (Codex).

## Verdict

**HOLD.** The individual seams have useful checks, but the integrated layer does not keep its setup, delivery, and freshness guarantees. The worst issue is concurrent landings for distinct streams of one repository mutating the same Git checkout without transaction-level exclusion. Separately, fresh stopped setup cannot satisfy worker readiness without starting early, release verification calls an absent CLI mode, and pusher/dashboard integration has lost documented behavior. These are source conclusions, not claims of reproduced runtime failures or failed model checking; the parent-run base gate passed build/vet and the four layer-6 packages, but the wider unit command failed in policy.

## Defects

1. **serious — Concurrent streams share the landing checkout.** `run/edges.go:81-89` launches a goroutine per land request, while `run/edges.go:271-278` derives the clone directory solely from the repository URL. `run/edges.go:125-138` passes it to each `LandPass`. Layer 3 excludes requests per **stream**, not repository (`steps/land.go:124-139`, `:168-170`). The real adapter checks out a base, merges heads, and finally reads mutable `HEAD` in separate commands (`edge/git/git.go:279-307`); conflict cleanup also resets that working tree (`:309-324`). Ordinary streams landing in one repository can interfere, producing spurious merge failures or a result assembled from another request's working state. **Counterarguments:** the chooser lock permits one run process, not one land goroutine; the edges mutex protects result/head maps, not these Git calls; Git's per-command locks do not cover the whole sequence. **Repair:** give concurrent landings private worktrees or serialize the complete mutable Git transaction by repository.

2. **serious — Fresh stopped setup cannot raise workers before its readiness check.** A new hook writes `PutRow` only (`verbs/hook.go:79-80`), which initializes the row down (`store/writes.go:114-130`). The normal up transition is `raiseSeen`, but `Ticker.Tick` returns on `Stopped` before calling it (`run/tick.go:158-165`). Setup requires bus presence and `row == "up"` (`cmd/nova-sprint/setup_workload.go:126`, `:164-178`); installing worker services does not write that state (`:92-116`). Thus fresh stopped setup with worker benches cannot finish even after successful worker hooks. Its refusal points to worker logs, which need not contain an error. **Counterarguments:** hook/heartbeat work mid-up but neither raises a new row; an already-up resumed fleet can pass; manually running `start` mid-up unblocks it, but contradicts the stopped readiness recipe. **Repair:** make presence readiness observable while stopped, or use a setup readiness predicate independent of the running tick, preserving no deal before start.

3. **serious — Failed folds refresh the run board as healthy.** `run/serve.go:151-171` retains a non-lock-loss error from `Fold`/`Tick`, but publishes the snapshot with the current tick time and only the roster error. `dash/run_cache.go:48-59` clears the error/alarm and accepts that time. Recurring store event-read failures with a successful roster read therefore keep old sprint data apparently fresh; `/healthz` uses that timestamp (`dash/server.go:153-163`). A later-page failure can also publish a partial fold as current. **Counterarguments:** successful idle folds legitimately refresh freshness; these are failed reads, whose error is logged but not sent to the board. Standalone cache failures preserve freshness (`dash/cache.go:148-153`), but run uses another path. **Repair:** publish only completed folds, retain the last successful timestamp on failure, and expose the failure in the cache.

4. **serious — Adoption invokes a shadow mode the CLI rejects.** `VersionAdoption.Ready` runs `run --shadow` after a version match and successful check (`verbs/setup_runtime_version.go:59-68`). Production wires it (`cmd/nova-sprint/setup_production.go:81`), and setup uses it for a requested version (`verbs/setup_runtime.go:117-120`). The run verb accepts only `listen=` (`verbs/table_coordinate.go:51`), and parsing refuses unknown flags (`verbs/flags.go:54-57`). Even a matching installed release cannot complete verification. **Counterarguments:** installation is deliberately delegated to nova-fleet; that does not remove this mandatory check. Its test fakes subprocess success instead of exercising the parser (`verbs/setup_runtime_version_test.go:17-27`). **Repair:** restore and wire a genuinely read-only shadow mode, or explicitly redesign adoption so it does not require a nonexistent command.

5. **serious — Observed Clear neither cancels old queued notices nor emits a summary.** The pusher stores queues/nudges (`run/push.go:39-42`), and `Observe` appends without epoch cancellation (`:58-73`). The fold clears inbox/refusals/inflight on epoch change, but leaves the pusher (`run/tick.go:115-124`). Event notices cover cards/judgements, not Clear summaries (`run/notices.go:20-54`). A later push sends the retained queue and saves its cursor under the current epoch (`run/push.go:124-149`); catch-up also scans old events without epoch suppression (`:89-109`). Obsolete notices can be sent **after Clear is observed**, without cancellation accounting. **Counterarguments:** the model permits an already-in-flight send racing Clear; this is a subsequent send from observed old backlog. Epoch-bearing deal commands protect their mutations, not the notification contract. Clear's live-consumer refusal does not exclude unsent terminal/judgement notices. **Repair:** cancel observed old backlog into the bounded Clear summary and save the cursor only after its confirmed delivery.

6. **serious — Slow push delivery blocks ticks and the board.** The loop cancels the planning budget, then calls `Ticker.Push` synchronously before publication (`run/serve.go:158-168`). Push sends and saves cursors serially per recipient (`run/push.go:130-149`); the actual bus edge allows five seconds per command (`edge/bus/bus.go:20`, `:74`). Several ordinary delayed/failing recipients can hold the loop for multiple tick periods with a healthy store. **Counterarguments:** sends are outside the store writer lock and bounded individually; neither property makes them off-tick or preserves the one-second cadence. **Repair:** schedule one serialized delivery worker independently and publish completed folds without waiting for recipient latency.

7. **minor — Standalone store-backed dash never gets a roster.** `services.Dash` creates `NewRecovering` and runs its store poller without using `s.roster` or calling `SetRoster` (`cmd/nova-sprint/services.go:104-125`). The cache's roster starts empty and is set through that setter (`dash/cache.go:30-39`). Unknown store rows deliberately map down at width zero, with only coordinators classified as friends (`dash/shim.go:179-205`). The standalone board therefore loses real widths/statuses, misclassifies ordinary friends and omits roster-only machines. **Counterarguments:** run-host feed and public pull wiring have roster data; neither repairs `dash --listen` without pull. **Repair:** refresh the roster and advertisements alongside standalone snapshots, with explicit roster failure.

8. **minor — Catch-up renders terminal events against today's state.** Each historical event is passed to `Observe(e, cold)` (`run/push.go:104-107`), but stream completion uses the supplied snapshot (`run/notices.go:43-45`, `:156-169`). If a stream completed while run was down and new unfinished producers were added before restart, its unsent completion notice disappears; multiple earlier terminal events can instead each generate a completion notice using final counts. **Counterarguments:** card transition notices correctly use event images; the defect is the stream-wide predicate. Live folds pass event-time snapshots, so this is restart-specific. **Repair:** reconstruct event-time state during bounded catch-up and render terminal notices from it.

## Promise gaps

- **serious, defects 2/4:** “every worker row hooked, `up` and dealable” (`docs/LAYER-6-RUN.md:292`) conflicts with the same table's fresh stopped, no-deal setup rule: current code needs a running tick to raise the row. “`--shadow` plans one tick on the live store without the lock, applies and sends nothing” (`:85-86`) names an unaccepted CLI mode.
- **serious, defects 3/6:** “A goroutine beside the tick” (`docs/LAYER-6-RUN.md:67`) is synchronous. “a failed fold does not refresh the clock” (`:583`) is contradicted by `run/serve.go:168`. That entry also promises a no-viewer monitor: `run/serve.go:69-94` starts heads and HTTP, but no freshness monitor; `dash/run_cache_test.go:23-28` calls `CheckFreshness` manually. Request-time health checks work when requested, but are not the independent alarm. **Repair:** wire the failure and clock-monitor lifecycle into the service, rather than only its test seam.
- **serious/minor, defects 5/8:** “It renders the notice at the event's sequence, not from the latest state” and “Once Clear is seen, old-epoch pending notices are cancelled” (`docs/LAYER-6-RUN.md:582`) describe absent behaviors. The paragraph is a historical foundation, not evidence of current validation; neither the main restart contract (`:81-83`) nor a later rule explicitly withdraws these semantics.
- **minor, defect 7:** both board modes are documented (`docs/LAYER-6-RUN.md:326-330`); a row pill should be “down if down, else held if held, else up” (`:338-339`). Missing standalone roster wiring invokes the unknown-row fallback instead.

## Model vs code

- **serious — Setup reachability is abstracted away (defect 2).** `tla/Setup.tla:70-76` makes `world[pc]` true in `Do`; it does not establish that production repair can make a bench up while stopped. `cmd/nova-sprint/setup_workload_model_test.go:20-61` checks two-bench predicates by directly constructing up/down rows. This is predicate correspondence, not fresh-state reachability. `SetupRun` represents early run startup and stopped control, but not this worker dependency. **Repair:** bind the composed setup/run presence transitions rather than weakening the stopped invariant.
- **serious — Atomic landing passes omit shared working state (defect 1).** `tla/LandEdge.tla:111-138` treats a pass as one action; production uses separate mutable Git commands across concurrent goroutines. Its tree invariants do not establish that the real adapter built each request's intended tree. **Repair:** establish adapter isolation and bind the returned tree to requested heads.
- **serious — Clear refinement is not implemented by this queue (defect 5).** `tla/RunClear.tla:60-67` suppresses old notices and records cancellation; `:82-85` saves only after required acknowledgements. It explicitly permits in-flight old sends and ambiguous counts (`:10-25`). The queue lacks that scan/summary state; the current Run mapping itself calls RunClear binding owed (`tla/RunTrace-MAPPING.md:198-199`). **Repair:** bind the actual queue to the refinement after implementation.
- **minor — Run mapping describes repaired defects and an obsolete fence.** It says a mid-fold Stop still permits apply, and observed lock loss still permits push (`tla/RunTrace-MAPPING.md:166-170`, `:194-211`). Current apply appends `store.Running{}` (`run/tick.go:244-246`), the loop exits before push on lock loss (`run/serve.go:159-162`), and `TestStopBetweenFoldAndApplyRefusesTheOp` exists (`run/tick_test.go:387`). The stronger model physical-sequence fence (`tla/Run.tla:241-246`) is not identical to Running: unrelated writes need not refuse the operation. **Repair:** update the mapping to distinguish repaired stopped behavior from the remaining stronger sequence abstraction, without presenting old failures as current evidence.
- `SetupHandoff` and `SetupChoices` were read too. Handoff expressly abstracts durable primitives/external-call completion and makes no Go/process secrecy proof (`tla/SetupHandoff.tla:4-20`); no general implementation or deployment claim is inferred from finite traces.

## Simplifications

- **minor — One dashboard publication/failure contract.** `dash/cache.go:129-153` and `dash/run_cache.go:48-59` own separate freshness/error resets and different lifecycles, contributing to defects 3/7. **Repair:** use one completed-read/failure interface and independently scheduled monitor for both sources.
- **minor — One current contract per entry point.** `docs/LAYER-6-RUN.md:247` prints a smoke-deal completion example, while `:292` and `:651-654` prohibit that up-time deal; the Run mapping retains superseded failures. **Repair:** label obsolete examples/mappings historical and point to the authoritative replacement.

This is a drift risk, not a proven end-to-end failure: the seat distribution contract was not established here. **Repair:** derive required routes/keys from one validated setup configuration or explicitly document the mandatory fixed set.
