Base: `43d849e29d0e4568ba6a1348a076a59259639938`. Report-only source review; no reproduction, new tests, or Go commands were run. Coverage was time-bounded: I inspected the layer contract and ENFORCED index, the run tick, pusher, notice derivation, service loop and edge dispatch; dashboard cache/pull/server; selected verb and CLI wiring; relevant run tests and Run model; I did not read every file in run, verbs, cmd, dash, their tests, or all layer models. Additional inspected paths include `verbs/{setup,setup_runtime_version,operate,judge,moves,check_landing,next,report,take,hook,flags,table_coordinate}.go`, `cmd/nova-sprint/{main,open,services,environment,edges,admit,lander,up_wrapper}.go`, `dash/{cache,run_cache,pull_cache,pull_handler,server,cursor,shim,cost,throughput}.go`, and `tla/{Run,RunClear,RunClearTrace,Setup,SetupRun,SetupHandoff,SetupChoices,LandEdge}.tla`, plus selected corresponding tests. Front-end assets, many setup/backup and verb files, most tests and remaining model/trace evidence were not completely read. This is not a whole-layer clearance.

## Verdict

The inspected portion is not sound against the documented contract. The most consequential issue is that a clear leaves old-epoch pending notices in the live pusher, so a delayed deal can be delivered after its sprint was cleared without the promised clear summary.

## Defects

1. **Serious — clear leaves old notices live.** `run/tick.go:113-124` resets inbox, refusals and inflight on an epoch change but retains `t.push`; `run/push.go:124-149` subsequently sends its queued notices. A failed pre-clear deal can therefore reach a row after clear, without the cancellation/count notice promised by `docs/LAYER-6-RUN.md:582`. On observing clear, cancel old-epoch queued notices and produce the specified bounded clear summary, including a way to handle an in-flight send.
2. **Serious — restart reconstructs terminal notices from the wrong point in history.** `run/push.go:89-107` passes the final cold snapshot to every historical event, and `run/notices.go:41-46` evaluates stream completion against that snapshot. If two producers land in separate unpushed events and both are terminal at restart, each event can produce a stream-complete notice even though only the latter completed the stream; later additions or state changes can also alter the reconstructed result. Reconstruct the snapshot at each event before deriving its terminal notice, as `docs/LAYER-6-RUN.md:582` specifies.
3. **Serious — roster failures bypass chooser health checks.** `run/serve.go:151-155` calls `Fold` directly on roster error rather than `Ticker.Tick`, whose health check is at `run/tick.go:151-153`; `run/serve.go:159-164` then pushes. Repeated roster failures can therefore leave a process running and sending without observing a lost lock or hook, contrary to the per-tick check and stop contract; check health before the roster-error fold and before any push, and propagate loss to the service loop.
4. **Serious — failed stop send remains in flight forever.** `run/tick.go:303-310` records a stop request in flight before `run/edges.go:101-107` sends it; on a send failure the edge logs and returns without a result, while only a consumed result removes the entry (`run/tick.go:291-297`), so a transient bus failure prevents re-dispatch of that request for the lifetime of the run. Return a retryable failure or remove the in-flight entry and reissue the stop.
5. **Serious — later apply errors discard effects of already accepted ops.** `run/tick.go:237-266` retains accepted IDs when a later apply or fold fails, but `run/tick.go:180-185` returns no edge requests on any error. If a preemption op commits and a subsequent op errors, the stop tied to that accepted withdrawal (`steps/preempt.go:57-64`) is not dispatched, and the changed state does not recreate that preemption; durably preserve and dispatch accepted effects while resolving errors and unknown outcomes.
6. **Serious — failed folds make stale board data look fresh.** `run/serve.go:151-168` publishes the snapshot and current tick time even when folding returns an error, while `dash/run_cache.go:48-50` resets its timestamp and alarm. A continuing store read failure can thus keep an old snapshot apparently current, contrary to `docs/LAYER-6-RUN.md:583`; also the run service never invokes the independent `CheckFreshness` (`dash/run_cache.go:62-67`), so a stalled tick has no no-viewer alarm. Publish freshness only after a completed fold and run a separate freshness monitor.
7. **Serious — a failed presence read becomes silence.** `run/serve.go:175-180` discards the `who` error and returns no names; `run/tick.go:158-159` keeps prior last-seen times, which `steps/limits.go:51-64` eventually uses to mark rows gone and withdraw their working consumers. A prolonged bus read outage can therefore withdraw live work without any successful observation that the rows disappeared; propagate and log the error and suspend silence decisions until presence is known.
8. **Serious — multi-target verbs hide already committed effects on later refusal.** `verbs/moves.go:82-98` applies each hold target separately but returns an empty output if a later lookup or move fails; `verbs/judge.go:39-54,178-195` does the same for group answers and multi-card drops; `verbs/verbs.go:143-144` prints only the resulting failure. For example, a valid first hold followed by an unknown target leaves the first hold committed while the caller sees no receipt for it; preflight and atomically apply the group, or return the committed effects alongside the refusal.
9. **Serious — serial pushes stall the chooser loop.** `run/serve.go:81-92,163-164` waits for `Push` before the next tick, and `run/push.go:130-144` sends recipients serially; a single bus send can take five seconds (`edge/bus/bus.go:18-21,74-75`), so one slow recipient delays all subsequent ticks and recipients, contrary to the separate pusher and one-second cadence (`docs/LAYER-6-RUN.md:51,67-70`). The roster read also precedes the budget and receives the service context (`run/serve.go:143-149`, `run/config_roster.go:39-42`), so a stuck read has no tick deadline. Bound observation and move bounded delivery off the chooser loop while retaining per-recipient cursor ordering and clear fencing.
10. **Serious — group-size confirmation is skipped when a group shrinks to one.** `verbs/judge.go:23-36` checks `--expect` only when the current member count exceeds one; a command copied when a group had two members can therefore answer the remaining single member with `--expect 2` rather than refusing the changed group promised by `docs/LAYER-6-RUN.md:374-375`. Require and compare the expected size whenever the argument names a group, including singleton groups, and fence the group against changes during application.
11. **Serious — version adoption invokes an unsupported shadow flag.** `verbs/setup_runtime_version.go:59-66` requires `run --shadow` after a matching release and check, but `verbs/table_coordinate.go:49-52` registers only `--listen` for run and `verbs/flags.go:54-57` rejects unknown flags. Consequently `up --version` cannot complete this verification on this build; implement the read-only shadow path or change the adoption gate to a supported equivalent.
12. **Serious — a recipient with no cursor forces a full cold-start log scan.** `run/push.go:89-109` takes the minimum of each hooked recipient’s cursor, whose absent map value is zero; `run/push.go:135-149` only writes a cursor when a notice is queued and sent. A newly hooked or quiet recipient can therefore make every restart scan the entire retained history, despite the bounded-from-cursor startup claim, delaying service as the log grows; define a safe subscription baseline or advance over known irrelevant events while retaining notice coverage.
13. **Minor — absent CI is judged before the configured wait.** `run/edges.go:136-142,162-171` adds a full 30-second poll interval on the first absent observation before any pause; with an allowed `ci_wait` of 1–30 seconds (`policy/validate.go:228-242`) it returns no-CI immediately, and the default wait is one interval short. Track elapsed time from the first absent observation before judging; the existing test counts passes rather than elapsed time (`run/edges_land_test.go:28-37`).
14. **Minor — run-fed throughput crosses a clear.** `dash/run_cache.go:37-44` publishes an epoch change without clearing samples; `dash/throughput.go:13-17` resets only when the landed count decreases. If a clear and new landings occur between feeds and the new count is at least the old count, the rate includes the prior epoch, contrary to `docs/DASHBOARD-LESSONS.md:126-130`; reset the sample window when the feed epoch changes.
15. **Minor — check falsely attributes a landing wait to a held stream.** `verbs/check_landing.go:45-49` reports a held stream as preventing a merging card from landing, while `docs/LANDING.md:224-225` says a hold never touches landing. The layer-6 check table also mentions a hold (`docs/LAYER-6-RUN.md:114`), so resolve that contradiction and report the actual landing state.
16. **Minor — restore prints after its next line.** `verbs/operate.go:168-172,180-189` appends admission lines after the hook output, which ends in `next:`; even an empty restored queue emits an admission line (`verbs/check_admission.go:72-74`). This breaks the last-line contract (`docs/LAYER-6-RUN.md:408-409`) for successful restore; emit admission before the final next line.
17. **Minor — stitch range does not represent a completed rung-1 stream.** `verbs/look.go:90-91` always compares the current base to the group branch, but rung 1 lands the card branch directly while only rung 2 rebuilds the group (`docs/LANDING.md:25-40`); after a rung-1-only stream, the group may still point at the old base and the range points backward rather than over the work to review. Retain the stream start base and final landed tip and report their range.
18. **Minor — judgement grouping is recorded but not implemented.** `run/notices.go:111-117` records `Group` per notice, but `run/push.go:158-166` ignores it and emits each line in one recipient envelope. Two open judgements of the same group receive individual commands rather than the promised group size, IDs and guarded group command (`docs/LAYER-6-RUN.md:365-375`); aggregate by group and construct the documented command.

## Promise gaps

- “Once Clear is seen, old-epoch pending notices are cancelled” (`docs/LAYER-6-RUN.md:582`): the pusher survives the reset at `run/tick.go:122-124` and sends its queue at `run/push.go:138-149`.
- “It renders the notice at the event's sequence, not from the latest state” (`docs/LAYER-6-RUN.md:582`): catch-up supplies the latest cold state to every event (`run/push.go:104-106`).
- “Check the lock connection is alive” each tick (`docs/LAYER-6-RUN.md:51-53`): the roster-error branch skips the check (`run/serve.go:151-155`).
- “a failed fold does not refresh the clock” (`docs/LAYER-6-RUN.md:583`): the loop publishes regardless of fold error (`run/serve.go:151-168`).
- “A group of n is one message” (`docs/LAYER-6-RUN.md:374`): the envelope ignores group metadata (`run/push.go:158-166`).

## Model vs code

`tla/Run.tla:238-246` requires a fresh physical-sequence fence on each modeled apply, while `run/tick.go:244-247` appends `store.Running`, not a universal `AtSeq` fence; an unrelated intervening write can therefore be permitted by a code op that the model refuses. `store/ops.go:70-76` distinguishes these conditions: this observation does not claim a stop can pass the atomic `Running` condition. `tla/RunClear.tla:10-14,65-66` suppresses old backlog once the new epoch is observed, whereas `run/tick.go:122-124` leaves the pusher queue intact (defect 1). `tla/Run.tla:272-290` treats a successful send as delivery of every event in the covered interval; `run/push.go:167-173` may replace remaining individual lines with a `next` summary and `run/push.go:143-149` advances to the final queued event. `tla/RunClearTrace.tla:3-6` explicitly acknowledges only rendered envelope members, while the production cursor advances across omitted members. The model does not establish that the summary exposes every omitted obligation; the contract itself identifies this integration as untested (`docs/LAYER-6-RUN.md:581`). The trace fixture also restricts its push to a whole tracked log (`run/run_trace_test.go:572-579`), so it does not demonstrate overflow recovery. This is a coverage gap, not a claim that every overflow loses an actionable obligation.

## Simplifications

`run/push.go:158-166` advertises grouping but performs only subject selection and line concatenation. A single explicit batching policy shared by notice construction and sending would make the grouping and cursor semantics easier to verify; resolve the documented per-recipient versus per-group wording first. Setup choice reads scan the full event history from zero for each question (`verbs/choices.go:27-45`), including the three consecutive reads at completion (`verbs/setup_runtime_completion.go:10-19`); a store-owned indexed answer lookup or a single shared scan would reduce repeated work, subject to preserving durable-answer semantics.
