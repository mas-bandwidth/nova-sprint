## Score: 8/10

nova-sprint v2 is the best cold-work tool I have ever been dealt a card by, and it does the hard 90% exactly right: a 40-verb surface where every verb prints its own next line, a refusal that is one line naming the fix, and a three-way exit code that never lies. It is not 10 because a cold AI cannot actually *start*: the first thing the tool prints to a stranger is a credential/fleet wall, there is no throwaway store to try the verbs safely, and the 8,860 lines of docs have no entry point. Those three are onboarding, not engine — the engine is the part that would already be a 10.

## What is good

- `nova-sprint help` is a complete, self-contained contract: its header states the exit-code contract ("Exit 0: done, the last line says next. Exit 1: refused ... Exit 2: bad usage, or the store, bus or an edge failed"), then groups all 40 verbs under `start:` / `work:` / `coordinate:` / `operate:` with each verb's role, its `refuses when`, and its `next`. I ran every verb's `help` from this alone and never needed another page to know what each does.
- `nova-sprint help take` is the exact shape an AI needs: `who`, `up` ("the store up makes at step 2"), `refuses when (and the fix it names)`, `next`. The pattern "refuses when (and the fix it names)" is the tool's one governing idea, and it is held consistently on every verb I tried.
- The refusal is never silent and never empty. `nova-sprint check` on my cold machine printed three `CHECK RED` lines, each naming its own fix, and embedded the subprocess stderr verbatim (nova-fleet's "CHECK MISSING ansible-playbook ...", nova-bus's "missing NOVA_BUS_REDIS (host:port)") before a final `SPRINT REFUSED check: 3 lines are red; the first: ...`. Nothing is swallowed; the raw tool output is carried up, which is what lets me trust it.
- The exit-code contract held under test: `version` -> 0; `up` without secrets -> 1 with "control-seat secrets configuration is incomplete: set NOVA_SECRETS_STORE, NOVA_SECRETS_KEY, NOVA_SECRETS_PINS and NOVA_SECRETS_SEAT"; `take`/`finish`/`judge`/`show`/`queue` without a bus -> 2 with "nova-bus who failed ... check NOVA_BUS_REDIS"; an unknown verb -> "unknown verb frobnicate: nova-sprint help". Every one named its fix, no silent zero.
- `docs/PLAYBOOK-WORKER.md` "The refusals you will meet" (lines 257-292) is a lookup table mapping every refusal a worker meets to its exact repair, and `docs/CORRECT-USE.md` "The one rule" (line 13) plus the chain table (lines 39-51) are the whole enforcement philosophy in one page: the tool enforces order instead of trusting an LLM to remember it.
- The deal/brief form is genuinely sufficient to work cold. My own card arrived as a brief that carried tier, PATHS, the done-when command, and the finish verb; `take`/`finish`/`read`/`report`/`release` cover every honest outcome (done, failed, harness fault, missing-route, going away), so an AI never has to invent an outcome the tool does not know.

## What gets it to 10

1. **A throwaway store verb.** `store.NewFake` and `store.NewFakeFrom` exist in `store/fake.go` but only as a Go test seam; there is no CLI path. Add a `nova-sprint demo` (or `--store fake`) so all 40 verbs can be exercised with no fleet. Done when: from a bare `git clone`, `nova-sprint demo` then `take`/`finish`/`read`/`judge`/`next` all run against the fake store and print their real next-lines with no PostgreSQL, Redis, Tailscale or nova-secrets.
2. **Fix what the bare binary prints.** `nova-sprint` with no arguments runs `next` and prints "NEXT this process has no sprint credential" -> `nova-secrets exec ...` (exit 0). A cold AI's first line is a wall that names a tool it does not have, and it is not told to read help. Change the no-args/cold path to print the reading path first (`next: nova-sprint help`, then `help playbook worker`) and to say nova-tools must be installed, before any credential requirement. Done when: the bare command's first `next:` line is a readable verb, and the credential/fleet requirement appears only after the AI has been pointed at help.
3. **A one-page quickstart.** `docs/SETUP.md` opens "This is what the setup must be; layer 6 makes it exact and this page becomes the walkthrough an AI runs" (lines 3-4) — it admits it is a contract, not yet a walkthrough. Add `docs/QUICKSTART.md` (install nova-tools -> `nova-fleet up` -> `nova-sprint up` -> `hook` -> `next` -> `take` -> `finish`), one line per step with its first output and first refusal, and point `help` and the top of `docs/README.md` at it. Done when: a cold AI follows only that page plus `nova-sprint help` and reaches a working `take` without opening the other 8,000 lines.
4. **One ordered bring-up, in one place.** Today the cold start is assembled from three separate refusals: `up` -> "control-seat secrets configuration is incomplete" (exit 1), acting verbs -> "nova-bus who failed ... missing NOVA_BUS_REDIS" (exit 2), `next` -> "no sprint credential". Make `nova-sprint up` (or `check`) print the complete ordered bring-up list (fleet -> tools -> secrets -> store -> bus -> identity -> `start`) with the exact command per step. Done when: one command produces the full order, and each subsequent refusal can simply be checked off against it.
5. **Per-verb doc pointers.** The 8,860 lines of docs have no "read this when" signal, so an AI reads layer history to find how to use a verb. Add to `help <verb>` a `docs:` line naming the one file and section that governs that verb (e.g. `help take` -> `docs:` `PLAYBOOK-WORKER.md "Work a card"`). Done when: every `help <verb>` names its governing section, and `help` names `QUICKSTART` first.

## Where I would be lost cold

1. **The bare binary points at a tool I do not have.** `nova-sprint` (no args) -> "this process has no sprint credential: run under nova-secrets exec ...", and `nova-secrets` is not installed because nova-tools is not set up. Verb: `nova-sprint`/`next`. The stall is that the first thing I am told to run depends on infrastructure I have not yet been told to install; the ordering (fleet before secrets before store) exists only in `docs/SETUP.md` prose, not in the tool.
2. **There is no way to try the verbs safely.** `docs/SETUP.md` step 1 requires the full nova-tools fleet (Tailscale, Redis, PostgreSQL, Ansible) before anything but `help`/`version`/`check` acts; the fake store is `store/fake.go`, a test-only seam, so "try the verbs against a throwaway store" has no CLI. A cold AI cannot practice `take`/`finish`/`read` without standing up a fleet it cannot yet stand up.
3. **The docs have no entry point.** `docs/README.md` is a layer-by-layer lock history and design log, not a "how do I use this"; the actual instructions are split across `SETUP.md`, `PLAYBOOK-WORKER.md`, `PLAYBOOK-COORDINATOR.md` and `CORRECT-USE.md`, and the tool's own `help` index — which is actually the best entry — is only reached if I already know to run it. Files: `docs/README.md` vs `docs/SETUP.md` vs `docs/PLAYBOOK-WORKER.md`.

## Tokens and time

- Reconstructing the cold-start order cost the most. The bring-up sequence is scattered across three refusals (`up` on secrets, acting verbs on `NOVA_BUS_REDIS`, `next` on the credential) and `docs/SETUP.md`, so I had to stitch the order (fleet -> tools -> secrets -> store -> bus) myself instead of reading it once.
- The docs volume. To reach a working mental model I read `SETUP.md` (90), `PLAYBOOK-WORKER.md` (312), `PLAYBOOK-COORDINATOR.md` (417), `CORRECT-USE.md` (287) and `docs/README.md` (223) — about 1,300 of 8,860 lines — because no single page is the walkthrough. The `help` index would have saved most of that if I had known to start there.
- The brief I was dealt is one dense blob (card spec + the "walk the tool / judge it" task + the review rubric) while the harness's `JOB.md` is skeletal (paths, done-when, finish line). The richest instruction lived in the deal message, not in a file I could grep, so the "walk every verb" part had no doc counterpart and was done by hand, one shell call per verb.
- Cheap, in contrast: `nova-sprint help` (one command, the whole 40-verb surface and the exit contract) and `help <verb>` (who/up/refuses/next per verb). These are the token-efficient parts and the parts I actually relied on.
