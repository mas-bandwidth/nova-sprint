## Score: 7/10

I am the AI using nova-sprint right now: I was dealt this card by it, I read the JOB.md, and I will finish with its verb. As a tool for an AI that has already been hooked into a running sprint, this is close to the best agent-facing CLI I have used: `help <verb>` is a uniform four-field contract for every one of the 40+ verbs (`who` / `up` / `refuses when` / `next`), every refusal is one line naming the one command that fixes it, exit codes are documented and meaningful (0 done, 1 refused, 2 store/bus/edge), and enforcement (hook-before-acting, one commit identity, DONE-WHEN-as-one-argv) lives in the tool rather than in the model's memory. The reason it is not a 10 is the cold-start promise the project sets for itself (SETUP 4: "an AI with no memory takes a fresh fleet from zero to a running sprint using only docs/README.md and the tool's own help") is not true for a lone AI today, and this very review card is the proof of the gap: I was dealt a card whose JOB.md carries the contract fields but not the task prose, the TEST, or the deliverable — the work reached me only through the deal/prompt, not through the job directory — and there is no documented way to rehearse any acting verb (`take`/`finish`/`read`/`up`) against a throwaway store before touching a live fleet. When the card is self-contained and a cold AI can run the verbs safely, this is a 10.

## What is good

- **`help <verb>` is a uniform contract, verb by verb (verbs/help.go).** I ran `help`, then `help` for every verb. Every table is the same four lines a cold AI needs: `who:` (who may run it), `up:` (what must exist first), `refuses when` (each refusal names its one fix), and a closing `next:` line. `help version` even ends `next: nova-sprint version`. This is the single best artifact in the tool, and it is the first thing a cold AI finds.
- **Refusals are one line, name the fix, and use honest exit codes (CORRECT-USE "The one rule").** Running `check` cold gave `CHECK RED` lines each naming its own fix, then `SPRINT REFUSED check: 3 lines are red; the first: ...` with exit 1. `next` cold did not refuse with a dead end; it printed `NEXT this process has no sprint credential` and the exact `nova-secrets exec` command to run. The `SPRINT REFUSED <verb>: <not true>: <fix>` shape held on every verb I tried.
- **Exit codes are documented and scriptable.** The help index opening line states all three: `Exit 0: done, the last line says next. Exit 1: refused, one line naming the fix. Exit 2: bad usage, or the store, bus or an edge failed.` A cold AI can branch on them without guessing.
- **Every output is self-carrying: two ends with `next: <command>`.** `take` prints the brief, the repository, the finish command, and ends `next: nova-sprint finish <card>@<gen> --head <sha> --as <you>`. The playbook's first rule, "run everything in your hand", and the push model (CORRECT-USE "Everything moves by push") mean nothing has to live in model memory.
- **Enforcement lives in the tool, not the model.** Hook-before-acting, the single git identity with author-email checks on `finish`, DONE-WHEN-as-one-argv, and the one-chooser lock are all refused by name (CORRECT-USE; LAYER-6). This is the right split between "tool" and "AI".
- **The project states its own cold-start bar and is honest about what is owed.** The dogfood gate is explicit (SETUP 4), README tracks the release gates (v2.0.x point releases, each a gate met), and CORRECT-USE lists what is Built vs. still owed. That honesty is rare and useful.

## Where I would be lost cold

1. **Fresh machine, no fleet: every useful verb refuses at the fleet or the store, and the recovery is another whole toolchain.** `next` and `check` correctly point me at `nova-secrets exec`, `nova-fleet check`, and `nova-bus who`, but stepping from "no tools" to a running store requires Tailscale, Redis, PostgreSQL, Ansible, and a human's key pastes — setup the docs assume rather than let a lone AI complete unattended. Gate 2 of SETUP 4 is stated but not demonstrated, so I am lost before the first verb that does anything.
2. **The card file does not carry the work.** My JOB.md holds kind, repository, base, checkout, `paths`, and `done-when` — but not the task prose, the TEST, or the deliverable description. That text reached me only through the deal/prompt, not the job directory. A harness that opens the job directory alone cannot learn what to build; I had to import context from outside the card.
3. **There is no sandbox, so I cannot rehearse.** The only verbs I can run cold are `help`, `version`, `next` (which names a missing credential), and `check` (which refuses red). To learn the real shapes of `take`/`finish`/`read`/`up`/`stream add`/`add` I would need a live sprint or a fleet I do not have; the only `--dry-run` flags are on coordinator verbs. I judged the tool without once running an acting verb.

## Tokens and time

- **Biggest cost: reading the operator docs to separate what I must do from design history.** PLAYBOOK-WORKER (312 lines), PLAYBOOK-COORDINATOR (417), CORRECT-USE (287), README (223), and LAYER-6 (906) restate the same refusals, prerequisite chain, and rules several times. I spent most of my budget distinguishing "what a worker must run" from "how the layer is built". A short minimum-reading path (item 4) would have saved the most.
- **Cheapest, highest-value: the verb help.** One `go run ./cmd/nova-sprint help <verb>` per verb gave me a uniform four-section contract; the grouped index (start/work/coordinate/operate) is the single best artifact.
- **The one question that cost the most unanswered search: "can I safely try a verb?"** The answer was no (no throwaway store, no dry-run for the acting verbs), and confirming that took more hunting than any single fact in the docs.
- `help playbook coordinator` dumps the worker playbook and the coordinator playbook concatenated (~731 lines of help output, docs/playbooks.go). That is a lot of tokens for a first onboarding; a pointer to the two files would read the same.
- Compiling and running `version`/`next`/`check`/`help` was quick and truthful; the tool's feedback loop is fast and reassuring. `go build`/`go run` needed a Go toolchain not on the default PATH (found at `/home/nova/sdk/go1.26.6/bin`), a one-line environment fix.
