## Score: 8/10

As the AI that is using this tool right now, I was dealt this card, read the JOB.md, and will finish with its verb. The verb surface, the refusals, and the reporting are genuinely excellent — this is the closest thing I have walked to a tool that is written *for* an agent rather than adapted for one, and the push-over-the-bus model plus the always-present `next:` line make a cold worker rarely lost on *what to run next*. It is not 10 because the cold-start path is not yet real: the card file (JOB.md) does not carry the work itself, there is no documented way to rehearse the acting verbs against a throwaway store without the whole nova-tools fleet, and this very review card's `done-when` is weaker than the rubric that grades it (it checks two of the five required sections). Those are three concrete, fixable gaps, each a card. When a cold AI can go from an empty fleet to a landed card against a scratch store with the card self-contained and the gate honestly enforcing the rubric, it is 10.

## What is good

- **`help <verb>` is the best artifact in the tool (verbs/help.go).** Every verb's table has four lines a cold AI actually needs: `who:` (who may run it), `up:` (what must exist first), `refuses when` (each refusal names its one fix), and a closing `next:` line. `version` even prints `next: nova-sprint help`. This is the single highest-value part of the whole project, and it is uniform across all 34 verbs I read.
- **Refusals are one line, name the fix, and use meaningful exit codes (CORRECT-USE "The one rule").** I ran `go run ./cmd/nova-sprint next` with no store and got `NEXT this process has no sprint credential / next: run under nova-secrets exec ...` — exit 0, actionable, not a wall of errors. The `SPRINT REFUSED <verb>: <not true>: <fix>` shape is kept everywhere.
- **The deal message and receipts are self-carrying.** `take` prints the full brief and ends `next: nova-sprint finish <id>@<gen> --head <sha> ...`; `finish`/`read` print one `FINISHED`/`READ` line. Nothing has to live in a model's memory between steps (PLAYBOOK-WORKER §Work a card).
- **Enforcement is in the tool, not the AI.** The hook-before-acting refusal (`hook in to the bus first: ...`), the single commit identity with author-email checks on `finish`, DONE-WHEN-as-one-argv, and the chooser lock are all refused and named, not hoped for (CORRECT-USE; LAYER-6 §3).
- **The project knows its cold-start bar and is measuring it.** The dogfood gate is explicit: "an AI with no memory ... takes a fresh fleet from zero to a running sprint using only docs/README.md and the tool's own help, and then does it again" (SETUP §4). The `Built:` notes in LAYER-6 and CORRECT-USE track what is actually shipped vs owed — unusual honesty.

## Where I would be lost cold

1. **Fresh machine, no fleet: every useful verb refuses at the fleet or the store, and the recovery is another whole toolchain.** `check` and `next` correctly point me at `nova-fleet` and `up`, but stepping from "no tools" to a running store requires Tailscale, Redis, PostgreSQL, Ansible, a human's one paste of a Tailscale token, and key pastes — setup that these docs assume rather than let a lone AI complete unattended. Gate 2 (cold AI sets up twice) is defined but not yet demonstrated, so today I am lost before the first verb that does anything.
2. **The card file does not carry the work.** My JOB.md holds kind, repository, base, checkout, `paths`, and `done-when` — but not the task prose, the TEST, or the deliverable description. That text reached me only through the deal/prompt, not the job directory. A harness that opens the job directory alone cannot learn what to build; I had to import context from outside the card.
3. **There is no sandbox, so I cannot rehearse.** The only verbs I can run cold are `help`, `version`, and `next` (which refuses). To learn the real shapes of `take`/`finish`/`read`/`up`/`stream add`/`add` I would need a live sprint or a fleet I do not have; there is no documented throwaway store or dry-run that shows me the behavior without committing to a real store. I judged the tool without once running an acting verb.

## Tokens and time

- **Biggest cost: reading the operator docs to separate what I must do from design history.** PLAYBOOK-WORKER (312 lines), PLAYBOOK-COORDINATOR (417), SETUP, CORRECT-USE (287), README (223), and LAYER-6 (586+) restate the same refusals, prerequisite chain, and rules several times. I spent most of my budget distinguishing "what a worker must run" from "how the layer is built". A short minimum-reading path (item 4) would have saved the most.
- **Cheapest, highest-value: the verb help.** One `go run ./cmd/nova-sprint help` per verb gave me a uniform four-section contract; the grouped index is the single best artifact.
- **The one question that cost the most unanswered search: "can I safely try a verb?"** The answer was no (no throwaway store, no dry-run for the acting verbs), and confirming that took more hunting than any single fact in the docs.
- Compiling and running `version`/`next`/`help` was quick and truthful; the tool's own feedback loop is fast and reassuring.
