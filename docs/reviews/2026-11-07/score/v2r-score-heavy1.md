# nova-sprint v2: independent continuation of the cold usability review

## Score: 7/10

The worker loop is well designed for an AI already invited into a configured sprint: explicit ownership, bounded generations, exact heads, receipts and pushed next actions reduce memory work. Seven remains my independent score after reading the required user documents and the complete captured help surface. The missing cold setup transcript and isolated practice environment prevent me from establishing that a new AI can safely get from clone to first landing. Several help and playbook contradictions also require source archaeology at precisely the moment a novice needs one authoritative instruction. This is a usability score for the reviewed interface, not proof that setup, delivery, landing or the dashboard works end to end.

## What is good

- `help` groups the real verb table into start/work/coordinate/operate, prints roles, and distinguishes pre-setup commands. `verbs/help.go` derives this map from the same table used for dispatch; it gives a cold AI a finite surface to inspect.
- `take` help explains a subtle custody rule clearly: the card is already in hand when dealt; take acknowledges it and stops nudges, and repeating take writes nothing. The worker playbook's first rule also states that the deadline starts at deal, making idle work visible rather than hiding it in an inbox.
- `finish` help names the full SHA, pushed branch, holder, nonempty work and commit identity checks. The worker playbook explicitly distinguishes a pushed head, a FINISHED receipt and actual landing. That is useful evidence discipline for AI reporting.
- `read` help and the worker playbook require an independent head review and a path/line/repair finding for fix. They distinguish a source read from a gate actually run at that head; they do not invite a reviewer to equate agreement with validation.
- `judge` offers only the choices of the actual judgement, and group answers use `--expect` to detect a changed group. `help judge` states both refusal repairs. A coordinator need not infer which operation is currently legal.
- `check` help covers admission, active policy, live holders, open judgements, waits and landing blockers rather than just connectivity. `docs/CORRECT-USE.md` also admits that a live row does not prove its individual job is executing. The coordinator playbook's custody section asks for the running command and head before calling a row busy.
- The supplied staging JOB gives one checkout, branch, inherited head, narrow report path, identity, acceptance command and completion owner. It let me start without private context. I distinguish this parent-written staging file from the generated bench JOB in `edge/worker/jobmd.go`; they are different execution routes.
