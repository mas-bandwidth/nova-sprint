# SPEC-LANDING: the ledgers the lander merges

A landing merges each queued card's head onto its base. Most files are the card's own: a
conflict there is the card's, and the card is reworked at the tip. The ledgers are the
files every card writes to keep the tree green, so a conflict there is the lander's, not the
card's: the lander merges the entries, and only a ledger it cannot merge is the lander's own
failure, which stops the stream. This page names the ledger set and the merge rule, one
place, so the scope rule and the lander read the same list.

## The ledger set

`internal/cardgen` is the one place: `cardgen.LedgerInPaths(p, catalog...)` says whether a
repository root relative path `p` is a ledger, and `cardgen.AlwaysInPaths` (the scope rule)
reads it (the built-in set), as the lander does (the built-in set plus the repository's
catalog). The built-in set:

- the roadmap data and the pages generated from it: `docs/fixes.sexp`, `FIXES.md`,
  `docs/roadmap.sexp`, `ROADMAP.md`;
- the evidence ledgers: `docs/roadmap-evidence/fixed-<leg>.sexp`
  (`cardgen.EvidenceLedger`, matched by glob), one entry per card, regenerated by the
  repository that owns them;
- the class ledgers under `internal/ci/testdata/` (`diffcheck.Ledger`);
- the AGENTS.md maps (`diffcheck.AgentsMap`);
- the keyed TLA+ tables and the tables lock: `tla/CASES.tsv`, `tla/RUNS.tsv`,
  `internal/sprint/TABLES.lock`;
- the docs catalog `internal/docs/catalog.go`.

A repository's own catalog names more ledgers with a `LEDGERS` line in its `AGENTS.md` or
`nova.sexp`, read at staging by `cardgen.CatalogLedgers(repoDir)` and passed to
`cardgen.LedgerInPaths`; absent, the built-in set stands.

## The merge rule

A merge stopped only on ledgers is resolved, not refused:

- the roadmap data and the evidence ledgers are merged entry by entry: each side only adds
  whole entries or only removes them in each conflicted stretch, the tip's additions before
  the card's, and an entry both sides change differently, or both add differently, is refused;
  a merged result must decode, and its entries must be exactly what the two sides did (both
  kept, in file order, no duplicate);
- a page generated from merged data (FIXES.md, ROADMAP.md) is taken from the tip and
  regenerated from the merged data, as `make roadmap` does; a page whose regeneration fails is
  the card's to redo;
- the class ledgers, the AGENTS.md maps and the keyed tables regenerate at the merged tree, a
  shrink-only ledger as the union of both sides' removals;
- an evidence ledger the base does not hold (an add/add conflict) keeps the shared header and
  footer once, then the tip's entries then the card's.

A ledger conflict the lander cannot resolve (a malformed entry) stops the stream with the path
and both entries in the judgment, as `merge --conflict-kind ledger` does; it never reworks the
card. A conflict in any file that is no ledger is refused as before, and the card is reworked.
