# s1. Introduction, terminology and conventions (rationale)

The owner, 2026-10-18: "it seems like we really need to create a SPEC for nova-sprint don't you
thinK? ... We keep drifting." `docs/SPEC-SPRINT.md` grew as a description of the code, with the
code's names, and each fix described what the code did after it; nothing held the code to what
it was for, so the same requirements (parallel reads, parallel merges, push and not poll) were
lost and restated. This standard is the other half: the requirements alone, in BCP 14 words,
each pinned by `internal/ci/standard_pins_test.go` to a test, a model property or a constant,
so a change that breaks a requirement fails its pin on the commit that makes it. `docs/SPEC-SPRINT.md`
stays as the descriptive document.

The pattern is the RocketNet standard's (mas-bandwidth/rocketnet, `standard/STYLE.md` and
`tools/conformance/check_rn_standard.py` on branch sprint/rocketnet-proof): an outline that is
the one source of the section list, one file per section so section cards never share a file,
pending sections listed and never failed, and every number or rule pinned. Here the checker is a
Go test, and a pin is a test, a TLA+ property or a Go constant rather than a C expression.

The thirteen hard rows (STYLE.md section 10) are the owner's requirements of 2026-10-18, each
quoted in its section's rationale. They are written and pinned from the first commit, in pending
sections too, so they are checked before the rest of their section is written. "Hard rows are
never weakened" is the owner's: a divergence pin states that the code does not yet hold one,
names the card that fixes the code and the test that card owes, and leaves the row as written.

The vocabulary keeps one word for one thing. "Machine" here is the running sprint, as in "the
sprint machine"; `docs/SPEC-SPRINT.md` uses "machine" for a fleet computer and "system" for
nova-sprint, and this standard calls a fleet computer a member.
